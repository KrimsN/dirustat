## Bugs

### QA-147: A scan root reached through a directory symlink to a UNC share counts as local; recycle silently deletes permanently

- **Severity:** S1 · **Likelihood:** Rare (needs a directory symlink to a network share on the scan root or one of its ancestors; creating one needs developer mode or elevation, but such links are a common way to put a NAS folder into a local tree) · **Scope:** Windows; `file.delete`, `file.delete_permanent`, `file.move`, `cleanup.run`; every host (UI, CLI, control, MCP)
- **Area:** `platform` `path.rs::classify_path_with` (lexical drive letter only), `engine` `cmd/file.rs::require_local_root`, `fsops::verify_location`, `platform` `system.rs::move_to_recycle_bin` · **Found by:** code
- **Build:** a7dff53, debug, Windows 11, not elevated, developer mode on
- **Status:** confirmed

**Steps to reproduce**
1. Fixture `F` (in the temp directory) with `victim\dirustat-qa-fixture.txt` and `victim2\a.txt`; a share that reaches it (here the existing `Users` share: `\\localhost\Users\<me>\AppData\Local\Temp\...\F`).
2. `mklink /D L\root \\localhost\Users\...\F` (a directory symlink, allowed without elevation in developer mode).
3. Scan `L\root` with the real `SystemPlatform` (`Session::new()`), then `file.delete {path: "L\root\victim\dirustat-qa-fixture.txt", confirm: true}`.
4. `file.delete_permanent {path: "L\root\victim2", confirm: true, i_understand_permanent: true}`; with `FakePlatform`: `file.move` of `L\root\victim` to `L\root\moved`.
5. List the recycle bin (`Shell.Application` namespace 10) for `dirustat-qa*`.
6. Control run: the same `file.delete` on a plain local fixture path.

**Expected (`docs/safety.md`, "Local roots only (positive validator)" and "Recycle bin"):** a network scan root is refused with `protected_path`; recycling is done only on fixed local disks, otherwise `unsupported` and the item is untouched.
**Actual:** `classify_path("C:\...\L\root")` is `Local` (drive `C:` is fixed). Step 3 returns `done: true`, the journal entry says `mode: "recycle"`, but the file is **not in the recycle bin** (0 items; the control run of step 6 puts its file into the bin, 1 item): the shell deleted it permanently because a network share has no bin. Step 4: `victim2` is removed over SMB, `file.move` moves `victim` on the share; `file.delete_preview` and the dry runs pass without any warning. `verify_location` does not object because the canonical root and the canonical parent both resolve to the same `\\?\UNC\...` location. `move_to_recycle_bin` checks `GetDriveTypeW` of the lexical root `C:\`, not of the real location.
**Reproduces:** 2/2 (fixtures `qa145s1`, `qa145s2`), plus 1/1 with `FakePlatform` (preview, dry run and move pass). Minimal repro: steps 1-3.
**Impact:** S1 under the project scale: a safety rule is broken (local roots only) and the reversible action the user chose (recycle) became a permanent deletion without the `i_understand_permanent` confirmation, reported as a successful recycle. This is the guard that QA-145 was fixing; the fix closed the mapped-letter vector but still trusts the lexical spelling.
**Suspected cause / pointer (guess):** `crates/engine/src/cmd/file.rs:337` (`require_local_root` classifies the lexical scan root), `crates/engine/src/fsops.rs:166` (canonical root is computed but never classified), `crates/platform/src/system.rs:38-39` (drive type of the lexical root). A fix: classify the canonical scan root and the canonical target (`\\?\UNC\...` is `Network`) in the preflight, and take the drive type for the recycle-bin decision from the real volume (`GetVolumePathNameW` of the canonical path).
**Evidence:** `145s recycle via symlink-to-UNC root: OK done=true ... file_exists_after=false`; `recycle-bin items named dirustat-qa*: 0`; control run: `recycle-bin items named dirustat-qa*: 1 / dirustat-qa-fixture.txt | ...\fx\qa145ctl\victim`; journal `{"mode":"recycle","ok":true,"op":"file.delete",...}`; `145 classify "...\qa145link\root": Local`; `145 file.move: OK done=true`.

### QA-148: Names consisting only of Unicode whitespace cannot be deleted at all; trailing `\n`/`\t` in a move destination gives `internal`

- **Severity:** S4 · **Likelihood:** Rare · **Scope:** Windows; all destructive commands, by path and by id; `file.move` destination validation
- **Area:** `engine` `protected.rs::key_impl` (the permissive key trims the whole path), used by `fsops::verify_location`, `ProtectedPaths::check` and `cmd/file.rs::check_destination` · **Found by:** code
- **Build:** a7dff53, debug
- **Status:** confirmed

**Steps to reproduce**
1. Fixture `root\sub\<name>` and `root\<name>` for each name `U+00A0`, `U+3000`, `U+2003`, `U+0085`, `U+00A0 U+00A0` (Win32 accepts all of them). Scan with `FakePlatform`.
2. `file.delete_preview`, `file.delete_permanent {dry_run: true}`, `file.delete_permanent {id, revision, dry_run: true}` and `file.delete` on each.
3. `file.move` of a file to `root\out\new<U+000A>` and `root\out\new<U+0009>`.

**Expected:** the files are deletable like `x<U+00A0>` (which works); a destination with a C0 character is `invalid_params` like `new<U+001F>`.
**Actual:** step 2, inside `sub`: every call `protected_path: the path reaches the target through a link or reparse point`; directly under the scan root: `protected_path: the scan root itself`; the tree has the node, and addressing by id does not help. The permissive key trims the whole path, so the last component disappears and the check compares the wrong parent or sees the scan root. Step 3: `internal: platform service failed: move failed: ... (os error 123)` because `check_destination` validates the trimmed components; nothing is moved.
**Reproduces:** 2/2 per name and per destination.
**Impact:** fails safe (nothing is touched), but such items can never be removed with the product, and the messages send the user looking for a link or a protected path that does not exist. Also the QA-139 side effect ("a name ending in NBSP cannot be addressed") is fixed for names with other characters but not for whitespace-only names, and the QA-141 fix does not reach a file named only `U+0085`.
**Suspected cause / pointer (guess):** `crates/engine/src/protected.rs:60` (`path.trim()`), consumed by `crates/engine/src/fsops.rs:157` and `crates/engine/src/cmd/file.rs:397`, `:518`, `:523`. A fix: use the exact key for the location check and destination validation; keep the trim only where over-matching is the goal.
**Evidence:** `139 ws-name "\u{a0}": node_found=true preview=ERR protected_path: ... through a link or reparse point | ... by_id_dry=ERR protected_path ...`; `139 ws-name at root "\u{85}": perm_dry=ERR protected_path: refused, protected path: the scan root itself`; `139 move dest "new\n": ERR internal: platform service failed: move failed: ... (os error 123)`.

### QA-149: Hardlinked file changed through another name: the stale name is refused once and its scanned size is stale

- **Severity:** S4 · **Likelihood:** Rare (a file with several hard links that was written through one name; for example package stores that hardlink files) · **Scope:** Windows/NTFS, portable scan
- **Area:** `scan` `read_dir`/`entry_from` (size and time from the directory listing), `engine` `fsops::verify_matches` (file mtime) · **Found by:** code
- **Build:** a7dff53, debug
- **Status:** confirmed

**Steps to reproduce**
1. `root\a.bin` (10 bytes), `mklink /H`-style hard link `root\b.bin`; wait 1 s; append 5 bytes through `a.bin`.
2. Scan `root`; `file.delete_permanent {path: root\b.bin, ...}` and `file.delete` on `b.bin`.
3. Variant: name the original `z.bin`, the link `a.bin` (so `a.bin` is the first name in scan order), append through `z.bin`, scan, dry-run both.

**Expected:** `b.bin` is deletable after a fresh scan; the tree shows the real size (15).
**Actual:** step 2: `stale_tree: the modification time changed since the scan` for both commands; a rescan 3 s later gives the same refusal; only after the refused attempt opened the file by that name does the next rescan succeed. Step 3: the tree holds `a.bin` = 10 bytes and a root total of 10 (real size 15), and `a.bin` is refused with `the file size changed since the scan`. NTFS updates the directory-listing copy of size and time only for the name that was used; the scan takes both from the listing, the identity check reads the file.
**Reproduces:** 3/3 per order, plus 1/1 for the rescan sequence.
**Impact:** fails safe and heals after one refused attempt plus a rescan, so S4 for the destructive part. The stale size is a pre-existing limitation of directory enumeration (not introduced by M4.10); the owner may want to triage it separately, since the MFT backend would read the real size and the two backends then disagree.
**Suspected cause / pointer (guess):** `crates/scan/src/lib.rs:530` (`entry_from` uses the listing metadata; the scan already opens multi-link files for `link_id_of`, which could supply fresh size and time), `crates/engine/src/fsops.rs:75` (mtime compared for hardlink names whose listing copy can be stale, the QA-142 reasoning applies).
**Evidence:** `tree=[("a.bin", 15), ("b.bin", 0)] a=OK ... b=ERR stale_tree: ... the modification time changed since the scan`; `142h round 0 (rescan after 3s): b.bin permanent=ERR stale_tree ...`; `142h round 1 (rescan after 6s): b.bin permanent=OK done=true`; `tree=[("a.bin", 10), ("z.bin", 0)] root_total=Some(10) real_size=15`.

## Per-defect detail

### QA-139 (exact request-path resolution)

- Original: `dupe` + `dupe<NBSP>` and `k` + `<KELVIN SIGN>`, same size and time: `file.delete_permanent` and `file.delete` by path remove only the named file (2/2 each).
- Variants: `dupe<U+3000>`, fullwidth `a.txt`, NFC `café` vs NFD `cafe<U+0301>`: only the named file removed. Lone-surrogate `f<U+D800>` next to literal `f<U+FFFD>`: by path `stale_tree` ("more than one entry matches", the message says "differ only in case", which is inaccurate but harmless), by id the literal file only. Case-sensitive directory (`fsutil setCaseSensitiveInfo`) with `a.txt` and `A.txt`: by path `stale_tree`, by id the right file. Non-ASCII case (`Ä.txt` requested as `ä.txt`): `invalid_params`, as documented (ASCII-only fold); `Ä.TXT` resolves. Move destinations `new<NBSP>`, `new<U+3000>`, `new<U+0085>` are created with the exact name.
- Residual: QA-148.

### QA-140 (colliding names in the subtree check)

- Original: two folders `d<U+D800>` and `d<U+FFFD>` with new files after the scan: `stale_tree` "holds entries whose names are identical after conversion to text", `sub` intact; rewritten file twin: same (2/2).
- Variants: two different lone surrogates (`d<U+D800>`, `d<U+DC00>`), the pair two levels below the target, `file.move` instead of delete, a file and a folder sharing the lossy text, a single lossy folder with a new file three levels below (detected via the real name; the tree holds the deep file, so the scan fix works). Unchanged twins: permanent refused (by design), recycle proceeds with `subtree_changed` set.

### QA-141 (C0-only control rule)

- `del<DEL>.txt`, `c1<U+0085>.txt`, `c1b<U+009F>.txt`, `<U+0080>lead.txt`, `end<U+009F>` recycle fine; a folder `c1<U+0085>dir` holding `inner<DEL>\f<U+009F>.txt` is removed permanently; a move to `m<U+0085>.txt` works. C0 names cannot be created on NTFS through Win32 (`os error 123`), so the remaining C0 refusal is only reachable through foreign volumes; `new<U+001F>` as a move destination is `invalid_params`. Residual: a file named only `U+0085` (QA-148).

### QA-142 (folder mtime)

- Original: junction created immediately before the scan, `file.delete_permanent` dry run on the folder: 0/50 `stale_tree` (two runs of 25). The junction itself (a link, whose time is still compared): 0/50. Related class: QA-149.

### QA-143 (free_space under the lock, thread leak)

- Stuck platform double (`free_space` sleeps 8 s) behind `Dispatcher::headless`: the first call returns `the volume did not answer in time` after 3.00 s; `session.state` 200 ms later answers in 0.12 ms; five further calls fail at once ("an earlier query of a volume has not returned yet"); the platform saw 1 call, at most 1 in flight; once the helper returns, the next call starts a new query (2/2).
- In-process `Session::execute` still blocks the lock holder 3.0 s and another thread waited 2.8 s: the desktop UI calls it from `refresh_volumes` under the lock (`crates/ui/src/app.rs:382`). Known and tracked as G-062; not counted against the fix.

### QA-144 (removal under the lock)

- 30,000 files in 100 folders, `engine.execute file.delete_permanent` on one connection, `session.state` polled every 20 ms on another: removal 4.8-4.9 s, 225-233 polls, worst latency 174-194 ms (the plan and subtree walk under the lock), `removal_in_progress: true` seen. During the removal `file.delete`, `file.delete_permanent` (also dry run) and `scan.start` are `not_enabled` in under 0.1 ms; `file.delete_preview` and `search.find` work. Afterwards: flag cleared, tree pruned (3 nodes), one journal entry, sibling untouched (2/2).
- Failure half-way (a file held open without share-delete): `internal ... os error 32`, slot released, `rescan_recommended: true`, journal `ok: false`, the retry is `stale_tree` naming the folder that is already gone (no prune of a partly deleted tree, as documented).
- Not fixed: the desktop UI runs `delete_dialog::confirm` with `Session::execute` under the session lock (`crates/ui/src/app.rs:696`, read, not run), and `cleanup.run` permanent holds the lock; both listed in G-062. The original QA-144 named the UI as possibly affected, hence "partially fixed".

### QA-145 (mapped network drives)

- Original, executed this time with a real mapping (`net use Q: \\localhost\Users`, drive type 4): all five spellings classify as `Network`; scan of a fixture through `Q:` works (scanning is allowed), every destructive command and `file.delete_preview` returns `protected_path`, `platform.free_space` returns `invalid_params`, the fake platform saw no call (2/2).
- Variant: directory symlink to UNC under a local drive letter: not refused, QA-147.

### QA-146 (`skipped_deep`)

- Chains of 2049, 2050 and 2052 levels: `match_path` matches the 2048 testable entries and reports 1, 2 and 4 skipped; with `kind: file` the skipped count is 1 (only the leaf passes the other filters); with `min_size` the same as without; name-only and empty queries report 0; a query that can never match still reports the skipped entries (conservative, matches the doc "may be incomplete"). Over control the field is present (2/2).
