Evidence PNGs from the control channel are named `ui-*` without `real`.
- **Not covered:** OS-level HiDPI scaling (only `zoom_percent`, the machine runs at 100 %), high-contrast theme (not implemented), access-denied folders (the fixture produced no scan errors), the MFT fast path (not elevated), `Ctrl+Q`, multi-monitor, long-running soak, screen-reader support, localization catalog, Linux/macOS. Menu click-through covered File, Edit, View and Help once each. Keyboard navigation inside the tree (arrows) is absent (known gap) and was not tested further.

## Bugs

### QA-101: Treemap silently drops detail: 50 000-tile cap leaves large empty directory blocks, worse when the window grows

- **Severity:** S2 · **Likelihood:** Often (any scan with more than about 50 000 visible tiles, which is every real disk; the empty area grows with window size) · **Scope:** all users, all platforms
- **Area:** `dirustat-treemap` `LayoutOptions::default().max_tiles`, `dirustat-engine::map` cache, treemap panel · **Found by:** ui (user report reproduced)
- **Build:** 5100219, release, Windows 11, not elevated
- **Status:** confirmed

This is the reported "treemap breaks when the window is resized". It is a persistent wrong picture, not a transient paint glitch.

**Steps to reproduce**
1. `target\agent-qa-ui\release\dirustat.exe --control 7990`.
2. `engine.execute scan.start {"path":"E:/sandbox/tmp/windirstat_rust/fixtures-local/100k-seed1"}`; wait until `session.state.scanning` is false (`nodes` = 100020).
3. Set the window to 1000x700 (`SetWindowPos`, or drag a border). `ui.screenshot` shows a full mosaic (`docs/qa/evidence/ui-100k-1000.png`).
4. Maximize the window (2560x1369 client). `ui.screenshot`: large flat dark rectangles with only a thin frame, no children, in the top-left and left-middle (`docs/qa/evidence/ui-holes-max.png`). They are directories that were left as leaf tiles and painted with the surface token.
5. Restore or shrink the window: the holes disappear. Maximize again: they return.
6. Same with `1m-seed1`: holes are visible already at 1184x761 and grow at 1484x861 (`ui-drag1m-end.png`). Hover over a hole shows a directory name and its total size (the node is real, only its children are not drawn).

**Expected:** every directory is subdivided down to the 2 px threshold documented in `docs/ui-design.md`, or the panel clearly says that detail was cut (and cuts the smallest tiles, not whole directories), at any window size.
**Actual:** the layout stops emitting tiles at a hard cap in breadth-first order; the remaining directories stay as empty blocks. A larger viewport produces more tiles of at least 2 px, reaches the cap earlier and shows more holes; a smaller viewport hides the problem. Rescan does not change it; shrinking the window recovers it. The control `ui.screenshot` shows the same picture as the real window (compared real-window captures with `ui.screenshot`), so a screenshot is a valid check.
**Reproduces:** 4/4 (100k at maximized, 1M at three sizes; 100k at 900x650 and 1000x700 full, at maximized holes).
**Impact:** the main view lies about the data for exactly the trees users scan; the user perceives it as corruption on resize. Core scenario broken, hence S2.
**Suspected cause / pointer (guess):** `crates/treemap/src/lib.rs:146` `max_tiles: 50_000` default, used by `MapState::new` (`crates/engine/src/map.rs`). The cache key (revision, bounds, mode) is correct and is not the cause; `bounds_for_size` floors to whole pixels correctly; no stale rect or DPI issue was found. Ordering by size (largest first within a budget) or a depth-aware cap would avoid empty big blocks.
**Evidence:** `ui-100k-1000.png`, `ui-holes-max.png`, `ui-holes-900x650.png`, `ui-drag1m-mid.png`, `ui-drag1m-end.png`.

Resize matrix (channel and OS driven): programmatic resize 600..1400 wide, drag from bottom-right and top-left (SC_SIZE 8 and 4), maximize, restore, 2000x300, 330x900, 160x120 on the 1 000-node tree: no defects (tiles always fill the panel, no gaps other than legitimate 3 px slivers, no crash). Aspect ratios 2000x300 and 330x900 behave (see QA-106 for the narrow case). Window size is not exposed by `ui.state`; sizes were taken from the screenshot size and Win32.

### QA-102: UI thread blocks about 2 s on every treemap resize step with a 1M-node tree

- **Severity:** S3 · **Likelihood:** Always with large trees · **Scope:** large trees (1M nodes), all platforms
- **Area:** treemap panel, `Session::map_view` · **Found by:** ui
- **Build:** 5100219, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan `fixtures-local/1m-seed1` (about 2.5 min, UI stayed responsive during the scan).
2. Time `SetWindowPos` of the app window (it returns when the UI thread pumps the size message): 3 steps at 1000, 1100, 1200 px wide.
3. Compare with the same call on a 100k tree and with a bare `GetWindowRect` (about 0.38 s of PowerShell start-up).

**Expected:** a resize step does not block the UI thread (`AGENTS.md` rule 8: never recompute the whole tree per frame, the UI thread never blocks).
**Actual:** 1M tree: 2.43, 2.44, 2.47 s per step; 100k tree: 0.47 s; idle `ui.state` round trip stays at about 0.14 s. During a live border drag the window freezes for seconds per step and a mid-drag capture shows a half-redrawn client area (`ui-drag1m-mid.png`: status bar overlapped, stale bottom edge).
**Reproduces:** 3/3 steps (and 2/2 drags).
**Impact:** the window feels hung while resizing on big disks; explains part of the "broken on resize" impression together with QA-101.
**Suspected cause (guess):** `Session::map_layout` has a single cache slot keyed by exact `[w,h]` bits, so every distinct size relays out the whole tree synchronously inside the frame (`crates/engine/src/map.rs:124`). A background layout thread, debounce on resize, or reuse of the previous layout while a new one is computed would fix it.

### QA-103: File-types panel ignores the size mode (always allocated)

- **Severity:** S3 · **Likelihood:** Always in logical mode · **Scope:** all users
- **Area:** `crates/ui/src/ext_panel.rs` · **Found by:** ui
- **Build:** 5100219, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan `fx-small`. `engine.execute view.size_mode {"mode":"allocated"}`, `ui.screenshot`; then `{"mode":"logical"}`, `ui.screenshot`.
2. Compare the percentage column of the File types panel with the tree (root 5.7 MiB vs 3.3 MiB) (`docs/qa/evidence/ui-ext-logical.png`).

**Expected:** extension sizes, percentages and ordering follow the selected mode like the tree and treemap.
**Actual:** tree and treemap change (5.7 MiB to 3.3 MiB), the panel shows the same 17.1 / 11.8 / 11.3 / 10.0 ... % in both modes.
**Reproduces:** 2/2.
**Impact:** violates golden rule 3 (never substitute one size for the other silently); wrong numbers in a core panel.
**Suspected cause:** `ext_panel.rs:109` `let mode = SizeMode::default();` instead of `session.map_size_mode()`. The cache key already includes the mode.

### QA-104: File-types panel: Type and Files columns invisible, size text clipped, sort glyph is a tofu box

- **Severity:** S3 · **Likelihood:** Always at default layout · **Scope:** all users
- **Area:** `ext_panel.rs` (`column_edges`), side panel width · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. Start the app, scan `fx-small`, window 1200x800 (`ui-01-initial.png`).
2. Look at the right panel. Resize the window between 700 and 1500 px: the panel stays about 95 to 140 px wide although `default_size(300.0)` is requested (also with the tree panel hidden).

**Expected:** `colour · .ext · size · % · files` (`docs/ui-design.md`), readable.
**Actual:** the extension name column (the only thing that explains what a colour means) and the Files column have zero width; the size reads `004.0 KiB` or `<iB` (left part clipped), the "Size" header reads `ize`, the sort indicator after "Size" is a tofu box (missing glyph; the tree header draws arrows correctly), and clicking the header cycles through hidden columns.
**Reproduces:** 5/5 screenshots.
**Impact:** the extension list cannot be used to read which extension a colour is; a documented core panel is effectively broken.
**Suspected cause (guess):** fixed `PERCENT_W/SIZE_W/COUNT_W` consumed first, `ext_right` clamps to the left edge; the panel is not given its default or minimum width; ▼/▲ in `header_label` are not in the font.
**Evidence:** `ui-01-initial.png`, `ui-ext-logical.png`.

### QA-105: `ui.state`/`ui.screenshot` time out while the window is minimized

- **Severity:** S3 · **Likelihood:** Always when minimized · **Scope:** Windows (likely all)
- **Area:** control bridge, `apps/dirustat/src/bridge.rs` · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. App running with `--control 7990`. Minimize the window (`ShowWindow(hwnd, SW_MINIMIZE)`).
2. `ui.state`: error after 10 s `timeout: the UI did not answer within 10s`. `ui.screenshot`: error after 40 s `timeout: the UI did not answer within 40s`. `session.state` still answers at once.
3. Restore the window: calls work again at once.

**Expected:** `ui.state` answers from the UI state regardless of window visibility; screenshot either works offscreen or fails fast with an actionable error (`docs/control-protocol.md` says 60 s for screenshots, the app says 40 s).
**Actual:** as above. An agent waiting on `ui.state` blocks for 10 s per call and gets an unhelpful `internal` error.
**Reproduces:** 3/3 (screenshot once, `ui.state` twice).
**Impact:** agent driving is fragile when a human minimizes the window; doc and behaviour differ in the timeout. Workaround: restore the window.
**Suspected cause (guess):** bridge requests are served inside the egui frame, and no frames run while minimized.

### QA-106: Treemap is starved or vanishes when the window is narrow or UI zoom is 150 %

- **Severity:** S3 · **Likelihood:** Often on small laptops and with zoom above 100 % · **Scope:** all users
- **Area:** `crates/ui/src/app.rs` `central()` panel layout · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. Window 1000x700, `ui.set_state {"patch":{"zoom_percent":150}}`, `ui.screenshot` (`ui-zoom150-real.png`): the treemap is a strip about 150 px wide and 550 px tall, the tree panel takes about 650 px.
2. Window 330x900: treemap and file types panels disappear entirely, the tree columns are cut (`ui-tall-real.png`); no scrollbar or hint that panels are hidden. At 160x120 only the menu, toolbar and status bar remain (`ui-tiny.png`, no crash).
3. 700x500: the treemap is a 90 px wide column.

**Expected:** the treemap (main view) keeps a usable minimum share; side panels shrink or collapse first; a hidden panel is indicated.
**Actual:** side panels take what they want, the central panel gets the remainder.
**Reproduces:** 4/4.
**Impact:** at 150 % scale (common on HiDPI laptops) the product's main visual is unusable until the user finds the separator.
**Suspected cause (guess):** `Panel::left("tree_panel")` content width forces the minimum; no `width_range`/max fraction.

### QA-109: No feedback in the panels during a scan

- **Severity:** S4 · **Likelihood:** Always · **Scope:** all users
- **Area:** panels, status bar · **Found by:** ui
- **Status:** confirmed

**Steps:** scan `100k-seed1`, then start `1m-seed1`; `ui.screenshot` after 5 s.
**Actual:** tree, treemap and file types still show the previous tree with its old numbers, the status bar left part still reads `100020 nodes` / old size, and only the status bar right part shows `Scanning: 8829 folders, 42307 files, 188.3 MiB`, preceded by a stray small glyph instead of a spinner. After `scan.start` through control the path box stays empty (`ui.state.path_text` is `""`). No determinate progress and no overlay on the stale views.
**Expected:** stale views marked (dimmed or labelled "previous scan") or cleared; path box shows the scanned path; spinner glyph renders.
**Reproduces:** 3/3. Cancel (`scan.cancel`, 0.12 s) works and keeps the previous tree with `Scan cancelled`. UI stays responsive during a 1M scan (`ui.state` about 150 ms, mostly client start-up).
**Impact:** confusing but not data-wrong.

### QA-110: `ui.state` does not round-trip through `ui.set_state`; shell `ui.*` commands are not drivable over control

- **Severity:** S4 · **Likelihood:** Always · **Scope:** agents
- **Area:** `UiBridge`, `apply_ui_patch` · **Found by:** ui
- **Status:** confirmed

**Steps:** `ui.state`, then feed its fields back: `ui.set_state {"patch":{"tree_expanded":[0]}}`, `{"scan":{...}}`, `{"elevation_help_open":true}`, `{"tree_revision":5}` are rejected with `invalid_params unknown field` (strict patch, fine) but `ui.state` emits them, so the full state cannot be echoed back. `engine.execute ui.toggle_tree|ui.theme_light|ui.zoom_in|ui.command_palette` return `unknown_command`; `ui.relaunch_elevated_help` is described in `docs/control-protocol.md` as "run through the bridge" but no method runs it, and `elevation_help_open` is not settable. Naming differs: `ui.state.ext_sort.column` vs `settings.get ext_sort.key`.
**Expected:** documented way to run every `UI_COMMANDS` entry, or a documented list of read-only fields. **Impact:** agents cannot exercise the elevation help window or expand tree nodes. Programmatic calls never opened a dialog (checked: only the app window and its helper windows existed after the command sweep).
**Reproduces:** 4/4.

### QA-111: Layout differs from `docs/ui-design.md`

- **Severity:** S4 · **Likelihood:** Always · **Scope:** all users
- **Status:** confirmed (mostly known gaps)

Observed vs doc: toolbar has no drive/folder picker (`list.drives` returns `[]` on this Windows machine; known G-014) and no search; tree columns are Name, Size, % of parent, Files, Modified (no folders, attributes); status bar shows node count, total and scan state but no path or free space; treemap is flat (no cushion shading, row 14 missing, though `settings.treemap.cushion` is `true`); View menu lacks `Largest files` although `engine.commands` declares `menu: View/Largest files` for `list.largest_files`; Help has only the elevation entry, no About; selecting a file in the treemap does not show its path in the status bar (tooltip only). Most items are listed as `missing` in `docs/target-app-parity.md`; the menu declaration without a menu item and the empty `list.drives` are the new findings.

### QA-112: Mixed path separators and non-canonical root name

- **Severity:** S4 · **Likelihood:** Always on Windows · **Scope:** Windows
- **Area:** `tree.path`, root node name, tooltip · **Found by:** ui
- **Status:** confirmed

**Steps:** `scan.start {"path":"E:/.../fx-small"}`; `tree.path {"node":5}` returns `E:/sandbox/.../fx-small\build_19.log`. `scan.start` with `.../fx-small/../fx-small` keeps the `..` in the root name (`session.state.root`). The treemap tooltip joins with `/` while the tree command joins with `\`.
**Expected:** one separator and a normalized root. **Reproduces:** 3/3. **Impact:** copy and compare of paths is awkward.

### QA-113: Selection feedback gaps

- **Severity:** S4 · **Likelihood:** Sometimes · **Scope:** all users
- **Status:** confirmed (a), once (b)

(a) Selecting a node whose tile is below the 2 px threshold (for example `select.node {"id":80}`, a 295 B file in logical mode) highlights the tree row and expands the tree but shows no mark in the treemap and no message. (b) `select.node` issued right after a scan finished returned `{"selected":80}` but `session.state.selection` was `null` a moment later (selection was cleared when the UI applied the completed scan); repeating the command later worked. Reproduction (b): 1/2.
**Expected:** a marker (or an "(too small to show)" hint); a command that reports success keeps its effect or is rejected while a result is pending.

### QA-114: Clicking the same tree header twice did not toggle the direction (unconfirmed)

- **Severity:** S4 · **Likelihood:** Unknown · **Scope:** unknown
- **Status:** cannot-reproduce reliably (possible artifact of the synthetic mouse driver)

**Steps:** real clicks (cursor move, press, release, 1 s apart) on the Size, % of parent and Modified headers: the first click selects the column with the right default direction, the second identical click often leaves `ui.state.tree_sort.descending` unchanged; a third click or a click after a small mouse movement toggles. The same worked for the File types headers and the code of `TreeSort::toggled` is correct. Needs a manual check with a physical mouse.

### QA-115: Polish

- **Severity:** S5
- After scrolling or sorting, the root row is partly hidden under the header (`ui-light-full.png`, first row cut).
- Menu check state is drawn as filled blue bars instead of check marks (`ui-menu-view.png`); the `Size mode` entry shows no current value.
- After scanning an empty folder the tree shows `No data. Enter a folder path and press Scan.` above a root row, and the treemap is an empty grey rectangle with no message.
- Mid-drag the tooltip and hover highlight stay at a stale pointer position (`ui-drag1m-mid.png`).
- Light theme: percent-bar labels cross the bar edge (`55.0%`, `34.4%`); contrast of the dim "Files" values looks below WCAG AA (visual estimate only, not measured).

## What worked (no defect found)

Smoke scan of 1 000, 100 000 and 1 000 000 nodes; totals and node counts match `session.state`; scan of an empty folder, missing folder, file path, UNC (`invalid_params` over control), empty path; cancel mid-scan (0.12 s, previous tree kept, status `Scan cancelled`); rescan; size mode switch for tree and treemap; `engine.commands` enabled flags (`scan.cancel` and `select.clear` disabled when nothing to do, `not_enabled` on direct call); strict `ui.set_state` validation (unknown fields, bad enums, zoom range 50..=300); light and dark themes; `Ctrl+=`, `Ctrl+-`, `Ctrl+0`, `Ctrl+Shift+P`, `Esc` shortcuts; selection sync tree to treemap and back (tree auto-expands and scrolls); ext selection highlighting in the treemap; unicode names; resize, maximize, restore, tiny window (no crash, no dialog from programmatic calls); `app.quit` exits cleanly and the key file is removed.

## Verdict: NO-GO

QA-101 (S2) makes the treemap wrong on every large tree and is exactly the user-reported resize breakage; QA-103 and QA-104 (wrong or unreadable file-types numbers), QA-102 (UI freezes on resize with big trees), QA-105 and QA-106 should be fixed or explicitly accepted before a release. Re-test after the fix with `ui-100k-1000.png` vs a maximized window on `100k-seed1` and `1m-seed1`.
