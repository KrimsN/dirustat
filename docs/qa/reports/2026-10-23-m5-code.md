# QA report 2026-10-23 · M5 code (export, duplicates, snapshots, treemap settings)

- **Commit:** 8f8783a (tree clean), debug build, `CARGO_TARGET_DIR=target/agent-qa-code`, Windows 11 (10.0.26200), not elevated, portable scan backend only.
- **Tester:** qa-code-tester agent. Throwaway tools (MCP driver, snapshot generator, settings loader) lived in the scratchpad, nothing was added to the repo. All fixtures were synthetic and in a temp directory; the only destructive command run was `file.delete_permanent` on a copy of a synthetic fixture. No real user data was scanned or touched (the user's `%APPDATA%\dirustat` was not read or written).
- **Method:** `dirustat-cli run --cmd ...` for single-shot export checks, and `dirustat-cli mcp` driven over stdio from a small script for stateful flows (scan, duplicates polling, snapshots, compare). Hostile `.dirsnap` files were hand-built with a valid BLAKE3 checksum (46 cases) and fuzzed (every byte flipped two ways, every truncation length, appended byte: 1700+ loads). The hostile settings file cases were run through `Settings::load_from` from a scratch crate.
- **Baseline:** `cargo test -p dirustat-engine`: 323 passed, 0 failed (no flaky tests seen). `cargo xtask ci` was not run (only the engine crate was touched by the features under test).

## Covered

- (a) `export.csv` / `export.json`: quoting, formula guard (name, extension and path columns), CRLF/control characters, limits and truncation, `node` subtree, `kind`, `max_depth`, `bom`, unknown/invalid params, path validation (relative, UNC, system dirs and 8.3/case/trailing-dot spellings, wrong extension, inside scanned tree incl. `..`, uppercase, 8.3 short name and a junction, existing file, read-only file, directory/symlink targets, `CON`/`NUL`/`COM1`/`LPT1`, ADS `:`, reserved characters, 300-char component, >260-char directory, 30000-char name), no temp-file leftovers, row counts and size sums versus the tree and versus the file system (hardlinks once).
- (b) `duplicates.*`: identical files, equal head/tail with different middle (partial-hash collision), `verify`, hardlinks, empty files, junction not followed, vanished/shrunk/locked files, `min_size`, `limit`, `path_prefix`, paging and `revision` checks, cancel/clear/restart, cancel during a 6 GB full hash (3 sparse-like files), scan during a search, wasted-bytes arithmetic.
- (c) `snapshot.*`: save/load round trip (JSON and CSV exports of live and loaded tree are byte-identical, also for a partial scan), overwrite/extension/inside-scan rules, 46 hostile files, fuzz, 3 GB and 0-byte files, directory/missing path, node cap, 4-snapshot cap, read-only refusal (`file.delete`, `file.delete_permanent`, `file.move`, `cleanup.run` with and without `dry_run`/`confirm`, by `path`, by `id`+`revision`, `platform.reveal`, `duplicates.find`), view lifecycle (scan, poll, close), compare semantics and invariants (delta equals the sum of changes, in both size modes, prefix variants, type changes, renames, include_dirs).
- (d) `treemap.look/grid/cushion/free_space`, `settings.set/get/reset`, hand-edited settings file clamping, free-space band math (code review of `split_bounds` plus the unit tests).
- (e) `session.state` after load/close/scan, selection handling, size sum invariants on a 515-node tree (every directory equals the sum of its children, logical and allocated, file counts; root equals `find` ground truth with hardlinks once).

## Not covered

- `export.png` (headless CLI answers `unsupported`; needs the desktop app): rendering, size limits, theme, PNG atomic write.
- The TCP control server, rate limits and truly concurrent commands (snapshot loads in flight, export while another command runs, the 4-snapshot cap under a race): the CLI/MCP host is single-threaded. `ui.*` commands and the UI (dialogs, comparison window, free-space band painting).
- The MFT fast path (no elevation), so portable-versus-MFT agreement for these features was not checked; real NTFS compression/sparse allocation numbers; network drives; non-ASCII/invalid UTF-16 file names on disk (only crafted in snapshots).
- Fuzz targets under `fuzz/` were not run. Performance budgets (the 245 MB hostile snapshot took ~25 s to load and ~14 s to save in a debug build; not judged).
- Hand-edited settings through the real app start-up path (only `Settings::load_from`).

## Bugs

### QA-150: `duplicates.find` with `path_prefix` drops files directly in the scan root

- **Severity:** S3 · **Likelihood:** Always (whenever `path_prefix` is given) · **Scope:** all users; any `path_prefix` including one equal to, or an ancestor of, the scan root
- **Area:** `dirustat-engine` `duplicates.find` (`crates/engine/src/duplicates.rs`) · **Found by:** code
- **Build:** 8f8783a, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. Create a temp folder `scan` with `big1.bin` (300000 random bytes) and `sub\big2.bin`, `sub\deep\big3.bin` (byte-identical copies), plus other files.
2. Via `dirustat-cli mcp` (or any session): `scan.start {path: <scan>}`, `session.poll`.
3. `duplicates.find {}` then `duplicates.status` / `duplicates.results`: one group with `big1.bin`, `big2.bin`, `big3.bin`, `wasted` 600000.
4. `duplicates.find {path_prefix: "<scan>"}` (the scan root itself; a trailing slash, or the parent folder, behave the same).

**Expected:** the same result as without a prefix, because every file is inside the prefix (the docs say the prefix restricts the search, matched at component boundaries).
**Actual:** `big1.bin` (a file directly in the root directory) is missing: the group has only `big2.bin` and `big3.bin`, `total_files` 4 instead of 5, wasted bytes understated (300000 instead of 600000). Files in sub folders are fine; `path_prefix: "<scan>/sub"` is fine.
**Reproduces:** 4/4 runs (prefix = root, root + `/`, parent of root, with and without verify). Minimal: any folder with two identical files where one is in the root directory, `duplicates.find {"path_prefix":"<root>"}`.
**Impact:** the result is silently incomplete and the wasted-space number is wrong. The feature is read-only so nothing is lost, but a user or agent deciding what to clean up from this list gets a wrong picture. A workaround exists (omit `path_prefix`).
**Suspected cause (guess):** in `size_candidates` the walk starts with `(root, root_path, prefix.is_none())`, so `inside` is `false` for the root directory whenever a prefix is set and `relation(root_path, prefix)` is never evaluated for it; only sub-directories get `Relation::Inside` (`crates/engine/src/duplicates.rs:454`).
**Evidence:** without prefix `total_files 5, names big1.bin big2.bin big3.bin a_copy.txt a3.txt`; with prefix = root `total_files 4, names big2.bin big3.bin a_copy.txt a3.txt`.

### QA-151: `snapshot.compare` shows spurious grown/shrunk between two scans of an unchanged tree

- **Severity:** S3 · **Likelihood:** Sometimes (8/20 runs on the minimal fixture) · **Scope:** all users with hardlinked files in two or more directories; portable scan (the MFT path was not checked)
- **Area:** `snapshot.compare`, portable scan hardlink accounting · **Found by:** code
- **Build:** 8f8783a, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. Create `hl\a\f` (50000 bytes) and a hardlink `hl\b\g` to it (`ln a/f b/g`).
2. In one session: `scan.start {path: hl}`, `session.poll`, `snapshot.save {path: ...\hl.dirsnap}`, `scan.start {path: hl}` again, `session.poll` (nothing on disk changes).
3. `snapshot.load {path: ...\hl.dirsnap, show: false}`, `snapshot.compare {base: 1}`.
4. Repeat the whole sequence several times.

**Expected:** `identical: true`, `changes: []` every time (the folder did not change).
**Actual:** in 8 of 20 runs `identical: false` with two changes: `a/f` (or `g`) `shrunk` by 24576 (allocated) / 50000 (logical) and the other name `grown` by the same amount. The total delta stays 0 but the list and counts are wrong, and `include_dirs` folder deltas are wrong too. The same happens on a larger fixture (3/8 runs).
**Reproduces:** 8/20 and 3/8 runs, so it is intermittent but frequent.
**Impact:** the compare feature cannot be trusted on trees with cross-directory hardlinks (WinSxS-like layouts, package caches): it reports changes that did not happen. The directory totals themselves are order dependent (the file's size is charged to whichever name the walk visited first), so a per-folder size of an unchanged tree differs between two scans, which also affects the tree and treemap. Core numbers differ between identical scans: this is at the border of S2; rated S3 because the grand totals stay right and the effect is limited to hardlinked data.
**Suspected cause (guess):** the portable walk is parallel, so which of several hardlink names is "first" (keeps the size, the others get `ATTR_HARDLINK_DUPLICATE` and size 0) depends on thread timing; the snapshot/compare keys on path and does not know that the owner may legitimately move.
**Evidence:** `{"delta":-24576,"kind":"shrunk","node_kind":"file","path":"a/f",...},{"delta":24576,"kind":"grown","path":"b/g",...}` with `"identical":false` for an unchanged folder.

### QA-152: `export.csv/json` `node` carries no `revision`; a stale id exports another subtree silently

- **Severity:** S3 · **Likelihood:** Sometimes (any tree change between reading the id and exporting) · **Scope:** control / MCP / CLI clients
- **Area:** `export.csv`, `export.json` (`node` parameter), `export.png` shares the parameter · **Found by:** code
- **Build:** 8f8783a, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. Temp folder `scan2` with `a.txt`, `sub\s1.txt`, `z\z1.txt`.
2. `scan.start`, `session.poll`; `tree.children {}` shows `sub` with id 2 and `z` with id 3 (revision 1).
3. `file.delete_permanent {path: <scan2>\a.txt, i_understand_permanent: true, confirm: true}` (a temp fixture; this prunes the tree and renumbers ids, revision 2).
4. `export.csv {path: <out>\stale.csv, node: 2}` (the id the client read for `sub`).

**Expected:** `stale_tree` (the docs say the subtree is "a node id with `revision`"), nothing written; or at least `invalid_params` for an unknown parameter `revision`.
**Actual:** success; the file contains the subtree of `z` (rows `z`, `z1.txt`), not `sub`. `revision` is not an accepted field (`unknown field`, the accepted list is `path, overwrite, allow_inside_scan, node, max_depth, kind, max_nodes, max_bytes, bom`), so a careful client has no way to make the call safe.
**Reproduces:** 2/2 runs. Minimal: `dirustat-cli run --scan <scan2> --cmd 'file.delete_permanent={...a.txt...}' --cmd 'export.csv={"path":"...","node":2}' --confirm`.
**Impact:** the export is read-only, so no data is lost, but the file silently holds the wrong data and the project already decided (QA-139 era, `docs/safety.md`) that bare ids must be revision-checked because they change on every prune. Same flaw would apply to `export.png`'s `node` (not run).
**Suspected cause (guess):** `TableParams` and `PngParams` have `node: Option<u64>` and `resolve_root` calls `node_by_index` without a revision (`crates/engine/src/cmd/export.rs:123,168`).

### QA-153: control-protocol export section does not match the implementation

- **Severity:** S4 · **Likelihood:** Always · **Scope:** anyone writing a client from `docs/control-protocol.md`
- **Area:** `docs/control-protocol.md` (Export), `export.csv/json` · **Found by:** code
- **Build:** 8f8783a · **Status:** confirmed

**Steps to reproduce**
1. `export.csv {path, subtree: <path or id>}` per the doc: `invalid_params: unknown field subtree` (real field `node`, id only, no path, no revision).
2. `export.csv` of any tree, read the header row.
3. `export.csv {kind: "dir"}` and `{kind: "file"}`.
4. `export.csv {max_bytes: 100}`.

**Expected (doc):** fields `path,name,kind,size,allocated,files,mtime,extension`; `subtree` (id with revision, or exact path); `kind` values per the doc for `export.csv`; `max_bytes` as a hard limit.
**Actual:** header `path,name,kind,depth,logical_size,allocated_size,file_count,mtime,extension,error,name_lossy`; the root row's `name` is the full root path; `kind` accepts only `all|files|dirs`; no `subtree`; `max_bytes: 100` still writes a 392-byte file (one row past the limit, as `params_doc` says, but the protocol doc does not). JSON rows use the same longer field names.
**Reproduces:** 4/4. **Impact:** documentation defect that misleads clients; also see QA-152. **Evidence:** `invalid params: unknown field 'subtree', expected one of 'path', 'overwrite', 'allow_inside_scan', 'node', ...`.

### QA-154: missing/unreadable file or unwritable target is `internal`, not `invalid_params`

- **Severity:** S4 · **Likelihood:** Always · **Scope:** all users, control/MCP/CLI
- **Area:** `snapshot.load`, `export.csv/json`, `snapshot.save` · **Found by:** code
- **Build:** 8f8783a · **Status:** confirmed

**Steps to reproduce**
1. `snapshot.load {path: <existing dir>\nope.dirsnap}` (typo, file does not exist); also `{path: <a directory named x.dirsnap>}`.
2. `export.csv {path: <dir>\<300 x "n">.csv}` (component over 255 chars), `export.csv` into a directory deeper than MAX_PATH (a 434-character directory that exists), and onto a read-only existing file with `overwrite: true`.

**Expected:** a handleable `invalid_params` ("file not found", "name too long") like the other path problems (existing directory check, extension, device names are all `invalid_params`).
**Actual:** `error[internal]: platform service failed: cannot read ...nope.dirsnap: <OS text>` / `cannot write ...`; for the over-long directory the message is `not found: ...\.dirustat-export-<n>.tmp` for a directory that exists (no long-path support: no `\\?\` handling). The `internal` code tells agents "bug in the app" instead of "your path is wrong".
**Reproduces:** 4/4. **Impact:** poor error handling, workaround is reading the message. Long-path exports are simply impossible (S4 on Windows).

### QA-155: a scanned empty folder cannot be exported or snapshotted

- **Severity:** S4 · **Likelihood:** Always · **Scope:** all users
- **Area:** `export.csv/json/png`, `snapshot.save` enabled predicate (`has_tree`: `tree.len() > 1`) · **Found by:** code
- **Build:** 8f8783a · **Status:** confirmed

**Steps to reproduce**
1. Scan an empty temp folder (`nodes: 1`).
2. `export.csv {path: ...}`, `snapshot.save {path: ...}`.

**Expected:** a one-row CSV / one-node snapshot (an empty folder is a legitimate baseline for `snapshot.compare`: "it was empty, now it grows").
**Actual:** `not_enabled: command not enabled: export.csv` / `snapshot.save` without a reason. `duplicates.find` on the same tree is accepted (`started`), so the guard is inconsistent.
**Reproduces:** 2/2. **Impact:** small functional gap and an unhelpful error.

### QA-156: `session.state {path:"/selection"}` is refused through `engine.execute` / MCP

- **Severity:** S4 · **Likelihood:** Always · **Scope:** MCP and `engine.execute` callers (the dedicated `session.state` control method was not run; the app bridge is untested)
- **Area:** control path-parameter validation (QA-117) vs `session.state` JSON pointer · **Found by:** code
- **Build:** 8f8783a · **Status:** confirmed

**Steps to reproduce**
1. `dirustat-cli mcp`, tools/call `session.state` with `{"path": "/snapshot"}` (also `/nodes`, `/selection`).

**Expected:** the pointer is applied (docs: "`session.state` accepts `path` as a JSON pointer").

### QA-157: small deviations and observations

- **Severity:** S5 · **Likelihood:** Always · **Scope:** all users
- **Area:** `snapshot.load`, `export.*` · **Found by:** code · **Status:** confirmed
- `snapshot.load` accepts a snapshot whose root is `C:\a\..\..\Windows\System32` (the root is only checked for being a local drive path; node names reject `.`/`..`, the root does not). Harmless today because destructive commands and id-to-path commands are refused for a shown snapshot, but `file.delete_preview {path}` (read-only) still reaches the real disk under a snapshot view.
- `snapshot.load` loads `ok.bin` (no `.dirsnap` extension check; `params_doc` says "a .dirsnap file").
- `max_bytes` is not a hard limit: one row more is written (1 GiB default gave 1,077,287,929 bytes for a hostile deep tree with 60 KB names, 189 rows). The `path` column of a deep tree makes the output quadratic (4096 levels of 60 KB names: 1 GiB reached in 189 rows); the default cap bounds it.
- `export.*` to a volume root (`C:\x.json`) is not refused as a "system folder" (it only failed with access denied on a non-admin account).
- `snapshot.compare {base: "1"}` says `unknown source "1": use "live" or a snapshot id` but ids must be numbers (`base: 1`).

## Verified OK (no defect found)

- Export path rules: all listed cases refused with the right code; junction into the scanned tree, symlink target, directory target, read-only target, ADS, reserved characters and device names refused; no temp files left behind after failures; overwrite needs `overwrite: true`.
- CSV: formula guard applied to the name and extension columns (`=`, `+`, `-`, `@`), RFC 4180 quoting, BOM, mtime extremes, control characters (C0 become U+FFFD, CR/LF inside a quoted cell are kept); JSON valid with control characters. Row counts equal node counts; every directory's logical/allocated/file_count equals its children (0 mismatches on 515 rows); root equals the file system total with hardlinks counted once.
- Duplicates: partial-hash collision (equal head and tail) not reported, `verify` consistent, hardlink names never candidates, junction not followed, vanished/shrunk/locked files counted in `problems` with samples, wasted bytes `(count-1) x size` correct, bad `limit`/`revision` rejected, cancel mid-hash of 3 x 6 GB files stops within one poll, clear/restart sequences behave.
- Snapshots: 46 hostile files and ~1700 mutated files were all refused with `invalid_params` (no panic, no acceptance except the original); caps (nodes, depth 4096/4097, name 65536/65537, 2 GiB, 4 snapshots) hold; huge sizes saturate at `u64::MAX`; destructive commands are `not_enabled` while a snapshot is shown via `path`, `id`+`revision` and without `confirm`; round trip of a live tree and a partial scan is byte-identical in JSON/CSV; compare deltas sum correctly in both size modes and type changes (file to folder) are reported as removed plus added.
- Treemap settings: every out-of-range, NaN/infinite (`1e39`), wrong-type and unknown-field value via `treemap.look` and `settings.set` is `invalid_params` with no change; a hand-edited file is clamped or reset to defaults; a file with an out-of-range f32 or an unknown field inside `look` is treated as corrupt and the whole file reverts to defaults (design choice, noted). `split_bounds` cannot reach `clamp(min > max)`: the minimum panel width (64) gives a maximum band of 32 against a minimum of 6.

## Verdict: GO with known issues

No S1 or S2 found: no panic, no safety rule broken, the read-only refusal while a snapshot is shown holds on every entry path tried, and the snapshot reader survived hostile and fuzzed input. Three S3 issues should be fixed before the release or accepted by the owner as known issues: QA-150 (`duplicates.find` with `path_prefix` silently drops root-level files), QA-151 (compare/scan noise from hardlink ownership flipping between scans; if the owner counts nondeterministic per-folder sizes of an unchanged tree as wrong numbers, this becomes S2 and blocks) and QA-152 (`export` `node` without revision). `export.png`, concurrency and the MFT path are untested here, so the verdict covers only what is listed under "Covered".
