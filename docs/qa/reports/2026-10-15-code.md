## Bugs

### QA-1: Treemap drops tiny children and leaves holes whose size depends on the viewport

- **Severity:** S2 · **Likelihood:** Always on any directory with a long tail of small files · **Scope:** all users, all platforms
- **Area:** `crates/treemap/src/lib.rs` (`layout_tree`), `crates/ui/src/map_panel.rs` · **Found by:** code
- **Build:** 5100219, debug and release, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. Build a weight list: 1 item of weight 20000 and 20000 items of weight 1 (one directory with such children).
2. Call `layout_tree` with bounds 400x300 and default `LayoutOptions` (`min_size 2.0`).
3. Sum the area of the emitted tiles of that directory and compare with the directory rect.
4. Repeat with bounds 800x600 and 200x150.

**Expected:** Children that are too small to draw are aggregated (or the parent area is filled as one block), so the directory rect is always fully covered. Resizing the window never makes blocks disappear.
**Actual:** Children whose rect is smaller than `min_size` on either side are dropped. The directory is then marked non-leaf (`leaf = false`), and `map_panel` draws non-leaf dirs as a frame stroke only, with no fill. The dropped area shows the background. The uncovered share changes with the window size, so the picture visibly changes while resizing. Measured on the repro: a large uncovered share at 400x300 and a different one at other sizes (numbers from the scratch run `tm`).
**Reproduces:** 2/2 runs (deterministic). Minimal repro: scratch crate `tm` calling `dirustat_treemap::layout_tree` as above.
**Impact:** Wrong treemap (core scenario) and matches the user report "resizing the window breaks block rendering of dirs/files". S2 per scale: wrong treemap output.
**Suspected cause (guess):** `kids` filtering by `min_size` after `squarify` without an "other" remainder tile, and `leaf` flag set to false whenever anything was emitted; the fill is skipped for non-leaf in `map_panel`.
**Evidence:** scratch `tm` output (uncovered percentage per bounds).

### QA-2: `max_tiles` cap starves the largest directories and makes detail depend on the viewport

- **Severity:** S2 · **Likelihood:** Often on big trees (more than 50k visible tiles) · **Scope:** all users, large trees
- **Area:** `crates/treemap/src/lib.rs` (`layout_tree`, stack traversal, cap check inside the child loop) · **Found by:** code
- **Build:** 5100219, debug, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. Build a tree of 1000 directories x 100 files with decreasing sizes.
2. Run `layout_tree` with `max_tiles 50_000` at 1920x1080, then at 1280x720.
3. Compare which directories received children tiles.

**Expected:** Cap is spent breadth-first or largest-first, so the biggest directories get detail first; the result changes smoothly with the viewport.
**Actual:** The work stack is LIFO, so the smallest sibling is popped and expanded first. When the cap is reached, the largest directories stay as one flat block (or without children) while small ones have full detail. Which directories are detailed also flips with the viewport size, because the number of tiles above `min_size` changes.
**Reproduces:** 2/2 runs. Minimal repro: scratch crate `tm`, starvation variant.
**Impact:** Wrong or misleading map on large disks; the most important (largest) areas lose detail. Together with QA-1 explains unstable rendering when resizing.
**Suspected cause (guess):** `Vec` used as a stack with children pushed in descending order; `break` on `max_tiles` inside the child loop.
**Evidence:** scratch `tm` output.

### QA-3: Windows portable scan counts hardlinked files N times

- **Severity:** S2 · **Likelihood:** Always when hardlinks exist (WinSxS, package caches, `git`/`pnpm` stores) · **Scope:** Windows, portable backend (non-elevated, the default for normal users and the MFT fallback)
- **Area:** `crates/scan/src/lib.rs` (`link_id_of`) · **Found by:** code
- **Build:** 5100219, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. In a temp dir create `a.bin` of 1 MiB, and `fsutil hardlink create b.bin a.bin`, `fsutil hardlink create c.bin a.bin`.
2. Run `dirustat-cli scan <dir>` (portable backend).
3. Read the total size.

**Expected:** 1 MiB counted once (`AGENTS.md`: hardlinks are not counted twice).
**Actual:** 3 MiB. `link_id_of` returns `None` on non-unix, so no hardlink dedup happens.
**Reproduces:** 2/2 runs.
**Impact:** Wrong totals; breaks a stated project invariant and portable vs MFT parity (MFT charges the size to the first node only). S2: wrong sizes.
**Suspected cause (guess):** dedup is implemented through inode ids on unix only; Windows needs the file index / volume serial from `GetFileInformationByHandle` (safe wrappers or std `MetadataExt` unstable fields may be a constraint under `unsafe_code = forbid`).
**Evidence:** CLI output of the two runs on the fixture.

### QA-4: UNC guard bypass over the control channel

- **Severity:** S2 (security rule of the control channel; arguably S1) · **Likelihood:** Rare (needs a client with the key) · **Scope:** Windows, control channel / MCP
- **Area:** `crates/control/src/dispatcher.rs` (`is_unc_path`, `engine_execute`) · **Found by:** code
- **Build:** 5100219, debug, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. Create a `Dispatcher` (headless) and send `engine.execute` with `scan.start` and `path` = `\\server\share` : refused as documented.
2. Send the same with `path` = `\??\UNC\server\share`.
3. Send `scan.open`-like or other path-taking commands with `\\server\share`.

**Expected:** Network paths are refused as documented in `docs/control-protocol.md` in every spelling, for every command that takes a path.
**Actual:** The `\??\UNC\` (NT namespace) spelling passes the check. The check also runs only when `command == "scan.start"`, so other path-taking commands are not guarded.
**Reproduces:** 2/2 runs (dispatcher level).
**Impact:** A network scan can be triggered over the channel, which the protocol promises to prevent (NTLM auth leak / slow hang on remote shares).
**Suspected cause (guess):** string-prefix test after `/` to `\` mapping covers `\\` and `\\?\UNC` only.
**Evidence:** dispatcher responses in scratch `ctl` (earlier version).

### QA-5: Portable and MFT backends disagree on allocated size

- **Severity:** S3 (S2 if confirmed on a real volume) · **Likelihood:** Often (resident small files are the majority on NTFS) · **Scope:** Windows, elevated MFT backend
- **Area:** `crates/scan/src/mft/collect.rs` (`sizes_of`), `crates/scan/src/lib.rs` (`entry_from`) · **Found by:** code (static; partly unproven dynamically, no elevated run)
- **Build:** 5100219
- **Status:** new (from code reading, not run on a real volume)

**Steps to reproduce**
1. Compare `sizes_of`: resident `$DATA` gives `allocated = 0`; sparse or compressed uses `compressed_size.unwrap_or(allocated)`.
2. Compare `entry_from`: `allocated = round_up(logical, 4096)` for every file.
3. Scan the same fixture with both backends (needs an elevated MFT run).

**Expected:** Same allocated totals on the same fixture, or a documented difference.
**Actual (by reading):** A 100-byte resident file is 0 allocated under MFT and 4096 under portable. Sparse and compressed files differ as well. "Size on disk" mode therefore returns different totals per backend.
**Reproduces:** not run dynamically (static finding, unproven numerically).
**Impact:** Fast path returns different data than the portable walk (S2 rule), downgraded to S3 because it is unproven and may be a documented policy ("see the module documentation").
**Evidence:** code references above.

### QA-6: Keyless local client can exhaust the control server

- **Severity:** S3 · **Likelihood:** Sometimes (requires a hostile local process) · **Scope:** all, control channel
- **Area:** `crates/control/src/server.rs` (`accept_loop`, `answer`, `RateLimiter`) · **Found by:** code
- **Build:** 5100219, debug, Windows 11
- **Status:** confirmed once; second run still to repeat

**Steps to reproduce**
1. Start the control server on 127.0.0.1 with a key.
2. Open 16 TCP connections without sending the key and keep them for the 5 s pre-auth window, repeatedly.
3. Send unauthenticated requests at more than 1000 req/s total.
4. Try a legitimate client.

**Expected:** Unauthenticated peers cannot take slots from, or consume the rate budget of, authenticated clients.
**Actual:** Connections beyond `max_connections` are dropped silently, and unauthenticated requests are counted against the global limiter, so a keyless peer can lock out the legitimate agent.
**Reproduces:** 1/1 (scratch `ctl`, TCP DoS version). Not repeated.
**Impact:** Local denial of service of agent control; no data exposure. Loopback only, hence S3.

### QA-7: `ui.screenshot` overwrites arbitrary `.png` files

- **Severity:** S4 · **Likelihood:** Rare · **Scope:** control channel with key
- **Area:** `crates/ui/src/screenshot.rs` · **Found by:** code
- **Build:** 5100219 · **Status:** new (static)

**Steps:** call `ui.screenshot` with `path` = an existing `.png` anywhere writable, `overwrite:true`.
**Expected:** Restricted to a documented directory, or at least refuse system/protected locations (`docs/safety.md`).
**Actual:** Any writable `.png` path is accepted, including UNC paths (no UNC rule here). Not demonstrated on a real file (no UI run).
**Impact:** Limited: only `.png` extension, temp+rename write, key required.

### QA-9: Protocol documentation mismatches

- **Severity:** S5 · **Likelihood:** Always · **Scope:** docs
- **Area:** `docs/control-protocol.md` · **Found by:** code · **Status:** confirmed
1. Examples mention `export.csv` and `file.delete`, which are not implemented.

## Checked without finding a defect

- Hostile JSON and oversized lines at dispatcher and server level; `deny_unknown_fields` and `page_limit` in engine commands.
- 30 `scan.start`/`scan.cancel` cycles through the dispatcher and 8 threads x 200 mixed concurrent commands: no panic, no deadlock, session usable afterwards (only `not_enabled` errors for commands unavailable in headless mode).
- `ntfs` parsers: all offsets, run lists, fixups, attribute lengths are bounds-checked in the reviewed code; no indexing, no unchecked casts found.
- Atomic `apply_patch` in UI state; CLI `--json` write is atomic.

## Verdict: NO-GO

Decided by QA-1 and QA-2 (wrong, viewport-dependent treemap, which is the user's resize report), QA-3 (wrong totals on Windows portable scans) and QA-4 (control-channel UNC rule bypass). QA-5 and QA-6 should be fixed before release or accepted explicitly by the owner. If the owner accepts QA-1..QA-4 as known issues, the verdict would be "GO with known issues", but QA-1/QA-2 are core-scenario defects.
