## Bugs

### QA-116: Deletion acts on the wrong file when two distinct on-disk names collapse to one path

- **Severity:** S1 (destructive action on the wrong target) · **Likelihood:** Rare (needs a file named with a trailing dot or a lone surrogate, created by something other than normal Windows tools, plus equal size and whole-second mtime) · **Scope:** Windows, all users; the portable backend (the MFT backend was not tested)
- **Area:** `engine` `cmd/file.rs` (`node_for_path`, `preflight`), `fsops::verify_matches`, `scan` `read_dir` (`to_string_lossy`, `name_lossy` never set) · **Found by:** code
- **Build:** 146ee68, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. In a temp dir create `root\dup` (14 bytes) and, through the extended path `\\?\<root>\dup.`, a second file `dup.` (14 bytes). Set the mtime of `dup` equal to the mtime of `dup.`.
2. Scan `root` (portable). The tree holds two nodes, `dup` and `dup.`. `file.delete_preview` for each id reports the paths `...\dup` and `...\dup.`.
3. Run `file.delete {id: <id of "dup.">, revision, confirm: true}` with `FakePlatform`.
4. Second variant: create `x<lone surrogate U+D800>.tmp` (19 bytes) and a literal `x\u{FFFD}.tmp` (19 bytes) with equal mtimes. Scan. Both nodes get the identical name `x\u{FFFD}.tmp` and `name_lossy == false`. Preview of both ids returns the same path. Delete the second id.

**Expected:** only the file the user selected is removed, or the command refuses because the node cannot be addressed by a unique path (lossy or Win32-aliased name).
**Actual:** variant 1: `dup` (the file the user did NOT select) is removed (`dup exists=false`, `dup. exists=true`), because Win32 path normalisation strips the trailing dot and `verify_matches` (kind, size, whole-second mtime) cannot tell the two files apart. Variant 2: the lone-surrogate file is unreachable by path, so the delete of either node removes the literal U+FFFD file (`lone exists=true literal exists=false`); the report and the journal name the wrong path as well.
**Reproduces:** 2/2 runs each variant. Test: `trailing_dot_collision`, `lossy_names` in the probe (see the regression candidates).
**Impact:** the selected-node-to-disk-object mapping is a path string, not a file id, so any aliasing name pair defeats every stale and location check. It is a rare precondition, but the consequence is deleting a file the user never saw, and the product's pitch is "safe delete". Blocks a release of the destructive commands until addressed (reject nodes whose `name_lossy` is set or whose name ends with a dot or space, and set `name_lossy` in the scanner; ideally compare a file id).
**Suspected cause / pointer (guess):** `scan/src/lib.rs` `read_dir` (`to_string_lossy`, `name_lossy: false`); `engine/src/fsops.rs` `verify_matches` (identity = kind + size + mtime in seconds).
**Evidence:** `DOT delete 'dup.' node: Ok(true)` / `after: dup exists=false 'dup.' exists=true`; `LOSSY delete id 5: Ok(true)` / `after: lone exists=true literal exists=false`.

### QA-117: `\\?\GLOBALROOT\Device\Mup\...` bypasses the UNC guard

- **Severity:** S2 (security hole in the control channel boundary, but the effect is limited to a stat call and a scan attempt, no data change; counted S2 rather than S1 because nothing is read or written on the share) · **Likelihood:** Sometimes (needs a client with the control key) · **Scope:** Windows, any client of the control channel or MCP
- **Area:** `control` dispatcher (`contains_unc_path`), `engine` `paths::is_unc_path`, `platform` `path.rs::validate_absolute` (accepts the `\\?\GLOBALROOT` namespace), `cmd/platform.rs` · **Found by:** code
- **Build:** 146ee68, debug, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. `Dispatcher::headless(share(Session::new()))`.
2. Send `{"id":1,"method":"engine.execute","params":{"command":"platform.free_space","params":{"path":"\\\\?\\GLOBALROOT\\Device\\Mup\\192.0.2.1\\share\\x"}}}` (192.0.2.1 is the RFC 5737 TEST-NET address, never routable).
3. Compare with `\\192.0.2.1\share\x` and `\\?\UNC\192.0.2.1\share\x`, which are rejected in microseconds with `invalid_params: UNC paths are not supported over control`.
4. Send `scan.start` with the same GLOBALROOT path.

**Expected:** all network namespaces (`\\?\GLOBALROOT\Device\Mup`, `\Device\LanmanRedirector`) are rejected like any UNC path, in microseconds.
**Actual:** step 2 returns `internal: platform service failed: stat failed: ... (os error 64)` after 8.3 s (first run 8.31 s, second 8.30 s; the lowercase variant 4.2 s). The call waits on the network and holds the session mutex for that time, so every other control request stalls. Step 4 starts a scan (`scanning:true`), which runs against the share for 8.4 s and then ends silently with an empty one-node tree (`nodes:1`).
**Reproduces:** 2/2 runs. Test: `unc_bypass_over_control`, `scan_root_bypass`.
**Impact:** the documented rule (no UNC/network access over control, safety.md) is not enforced for this namespace. A real reachable host would be contacted (SMB authentication attempt, possible credential leak by NTLM to an attacker-chosen host) and a hung host stalls the whole control session. Narrower than QA-4 of the earlier run (that was a `\??\UNC` bypass); this is the same class again, so the guard should be positive (allow `X:\` and `\\?\X:\` only) rather than a deny list.
**Suspected cause / pointer (guess):** `engine/src/paths.rs` `is_unc_path` checks the prefixes `\\?\`, `\??\`, `\\` on the first 16 characters and then requires `UNC`; `\\?\GLOBALROOT` passes as a "local extended path".
**Evidence:** `FREE "\\\\?\\GLOBALROOT\\Device\\Mup\\192.0.2.1\\share\\x" -> 8.3139801s {"error":{"code":"internal",...os error 64}}`; `SCAN ... finished after 8.4326152s ... "nodes":1`.

### QA-118: Stale check covers only the target node; deeper changes are deleted unseen

- **Severity:** S2 (data loss of content the user was never shown, permanent mode) · **Likelihood:** Sometimes (the window between scan and delete can be hours; any active folder qualifies) · **Scope:** all users, all platforms; worst in `file.delete_permanent` and `cleanup.run` with `permanent`
- **Area:** `engine` `cmd/file.rs` (`preflight`, `execute`), `fsops::verify_matches` · **Found by:** code
- **Build:** 146ee68, debug, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. Fixture `root\sub\{a.txt, deep\b.txt}`. Scan.
2. `file.delete_permanent {path: sub, dry_run: true, confirm: true}` reports `count=4 files=2`.
3. Outside the app add `sub\deep\NEW_UNSEEN.docx` ("precious") and rewrite `sub\deep\b.txt` with different content and size.
4. `file.delete_permanent {path: sub, i_understand_permanent: true, confirm: true}`.

**Expected:** `stale_tree` (nothing changed), or at least a report that the folder contents differ from the preview; at minimum `partial_tree`/`rescan_recommended` style refusal for permanent mode.
**Actual:** `Ok(count 4, done true)`; `sub` is gone, including the new file and the modified file; revision 1 -> 2. The re-validation compares kind, size and mtime of the folder node only (the folder's own mtime changes only for direct entries, and for directories the size check is skipped), so changes at depth are invisible.
**Reproduces:** 2/2 runs. Test: `deep_change_not_detected`.
**Impact:** the "stale tree is re-validated before any action" promise in `safety.md` holds only for one level. In recycle mode the data is recoverable; in permanent mode it is lost. Mitigation: the user confirmed a preview that no longer matches. Needs a walk of the real subtree against the model before a permanent folder delete (or an explicit "subtree not verified" flag in the response/dialog).
**Suspected cause / pointer (guess):** `fsops.rs` `verify_matches` for `NodeKind::Dir` checks only kind (and optionally mtime); `execute` re-walks nothing.
**Evidence:** `DRY count=4 files=2`, `PERM result: Ok((4, true))`, `sub exists after: false (rev 1 -> 2)`.

### QA-119: Second and later hardlink names can never be deleted

- **Severity:** S3 · **Likelihood:** Often on trees with hardlinks (Windows component store, package caches, pnpm/cargo) · **Scope:** all users on the portable backend
- **Area:** `scan` `apply` (later hardlink names get `logical_size = 0`), `fsops::verify_matches` · **Found by:** code
- **Build:** 146ee68, debug, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. Create `hl_a.bin` (500 bytes) and `hard_link` it as `hl_b.bin`. Scan.
2. `file.delete_preview` for `hl_a.bin` returns OK, for `hl_b.bin` returns `stale_tree`.
3. `file.delete` of `hl_a.bin` succeeds; `file.delete` of `hl_b.bin` returns `stale_tree`.
4. Fixture with `x_a.tmp` and a hardlink `x_b.tmp`; `cleanup.run {id:"temporary-files", confirm:true}`.

**Expected:** each name is deletable (the size check should use the real per-name size, or skip the size comparison for nodes flagged as hardlinked); the cleanup does not report a failure for an item it correctly selected.
**Actual:** the tree stores 0 for the second name, `meta.len()` is 500, the check reports "the file size changed since the scan". Even after a rescan the later name stays at 0 (the order decides), so the failure is permanent. The cleanup reports `deleted=1 failed=1` with `stale tree, nothing changed: the file size changed since the scan`.
**Reproduces:** 2/2 runs. Test: `hardlink_delete`.
**Impact:** fails safe (nothing wrong is deleted), but a documented feature (delete, cleanups) cannot handle a common file class, and the error tells the user to rescan, which does not help.
**Evidence:** `HARDLINK preview hl_b.bin: stale_tree`, `HARDLINK cleanup: deleted=1 failed=1`.

### QA-120: `cleanup.preview` and `cleanup.run` have no time budget

- **Severity:** S3 · **Likelihood:** Rare for built-ins; Sometimes for user-defined cleanups with many globs · **Scope:** all users; also over control/MCP (session mutex is held)
- **Area:** `engine` `cleanup.rs` (`select`, `Compiled::matches`), `cmd/cleanup.rs` · **Found by:** code
- **Build:** 146ee68, release for timing
- **Status:** confirmed

**Steps to reproduce**
1. Build a tree of n nodes with 240-char names of `a`. Save a cleanup with 64 name patterns of the form `*a` x127 followed by `b` (256 chars each, never matches).
2. `cleanup.preview {id}` for n = 2000, 10000, 40000.

**Expected:** like `search.find`: a time budget (`budget_exhausted`) so a request cannot run unbounded; the glob matcher must not be O(pattern x text) per pattern per node without a cap.
**Actual:** 0.27 s, 1.34 s, 5.6 s (linear in n; 64 patterns x 256 chars is the maximum the validator allows). On a 1M-node tree the same definition would take roughly 2.5 minutes, with the session locked and no cancellation. Scan exclusions with the same 64 patterns cost only 0.46 s for 3000 files, so the scan path is fine at this size.
**Reproduces:** 2/2 runs. Test: `cleanup_pathological_timing`.
**Impact:** hang-class on adversarial or accidental input; the scope is limited by pattern caps, so S3.
**Suspected cause / pointer (guess):** `select()` is an unbudgeted DFS and calls every glob for every node.
**Evidence:** `CLEANUP preview n=40000: 5.6s`.

### QA-121: Deep tree plus `match_path` consumes the entire 10 s search budget under the session lock

- **Severity:** S4 · **Likelihood:** Rare (needs 100k-deep chains, possible only with junction-free but extremely deep trees or synthetic trees) · **Scope:** all users
- **Area:** `engine` `search.rs` (path building for `match_path`) · **Found by:** code
- **Build:** 146ee68, release
- **Status:** confirmed

**Steps to reproduce**
1. Tree: a 100,000-deep directory chain with one leaf file.
2. `search.find {query:"leaf", match_path:true}`; and `{query:"d", match_path:true, kind:"dir", limit:10000}`.

**Expected:** path building is O(total) with incremental prefixes, or bounded far below the budget.
**Actual:** both calls run until the 10 s budget (10.02 s and 10.51 s) and return `budget_exhausted:true` (51,455 of 100,000 dirs reached). Behaviour is safe (no panic, bounded), but the session is blocked for 10 s per call.
**Reproduces:** 2/2 runs. Test: `deep_tree_paths`.
**Impact:** quadratic cost (path length x depth); degraded but bounded.

### QA-122: UNC guard rejects legitimate queries and exclude patterns

- **Severity:** S4 · **Likelihood:** Sometimes (regexes with escaped backslashes, wildcard `\\*`, URLs-like `//` substrings) · **Scope:** control/MCP only (the UI and in-process API are not affected)
- **Area:** `control` dispatcher `contains_unc_path` · **Found by:** code
- **Status:** confirmed

**Steps to reproduce**
1. Over `Dispatcher::handle_line` send `search.find {query:"\\\\d+", mode:"regex"}`, `{query:"a//b"}`, `{query:"\\\\*", mode:"wildcard"}`, and `scan.start {path:<ok>, exclude:["a//b"]}`.

**Expected:** only parameters that are paths (`path`, `destination`, `paths`) are checked.
**Actual:** all four return `invalid_params: UNC paths are not supported over control`. The check scans every string value of the params (also a name in `cleanup.save` passes only because it contains no separator pair).
**Reproduces:** 2/2 runs. Test: `control_unc_false_positive`.
**Impact:** agents cannot search for or exclude patterns with doubled separators; no safety impact (fails closed). The fix must keep QA-117 in mind: a per-key allow-list for path-typed keys plus a positive path validator.

### QA-123: `file.move` accepts reserved device names as destination

- **Severity:** S4 · **Likelihood:** Rare · **Scope:** Windows
- **Area:** `engine` `cmd/file.rs` (`destination_component_problem`, `check_destination`) · **Found by:** code
- **Status:** confirmed

**Steps to reproduce**
1. Temp fixture, real platform rename on the temp dir only. `file.move {path: root\keep.txt, destination: root\CON, confirm:true}`; repeat with `COM1`, `aux.txt`, `LPT1.log`, `nul.tar.gz`, `CLOCK$`.

**Expected:** `invalid_params` for names Win32 treats as devices (`NUL` was refused only by accident: the platform reported "destination already exists").
**Actual:** `done:true` for all but `NUL`; the directory listing shows `CON`, `COM1`, `aux.txt`, ... created. `CON` and `COM1` cannot be opened, listed or deleted with ordinary Win32 paths (the probe cleaned them only through the `\\?\` form). `file.delete_permanent` of the moved `CON` also reported `done:true` and removed it in the fixture, so the product can later clean it, but Explorer and shell tools cannot.
**Reproduces:** 2/2 runs. Tests: `move_destination_oddities`, `reserved_name_delete`.
**Impact:** a rare self-inflicted filesystem oddity; no data loss. Side note, not a bug: a destination such as `y\..\..\z` is normalised and may land outside the scan root (the documented behaviour allows destinations outside the tree).

### QA-124: CLI `run` never persists the journal

- **Severity:** S4 · **Likelihood:** Always for CLI users · **Scope:** `dirustat-cli run`, all platforms
- **Area:** `apps/dirustat-cli` `cmds.rs` (`Session::new()` without `set_journal_file`) · **Found by:** code (static; the CLI was not run against a destructive command, see Not covered)
- **Status:** unproven by execution

**Steps to reproduce**
1. `dirustat-cli run --scan <temp fixture> --cmd file.delete_permanent={...} --confirm`, then inspect the journal location documented in `safety.md`.

**Expected:** destructive actions are journaled to the persistent file like in the app.
**Actual (from code reading):** `set_journal_file` is called only by the desktop app; the CLI keeps the journal in memory and it disappears at exit. `file.journal` in the same invocation does return the entries (verified in the engine through `journal_and_dryrun`, which writes a line per action when a file is configured).
**Impact:** the audit trail of safety.md is missing for the headless path that agents use.

## Probed and found correct

- Protected paths refused: scan root itself, drive roots, `Windows`, `Program Files`, profile internals, admin shares; path forms with `..`, different case, `\\?\` prefix and forward slashes resolve to the same node and are checked; 8.3 and ADS forms are rejected with `invalid_params`.
- `confirm` is required for every destructive command including dry runs (`not_enabled` over control without it); permanent mode needs `i_understand_permanent`; default mode is recycle.
- Revision handling: wrong type (float, string, negative, null) -> `invalid_params`; `u64::MAX` -> `stale_tree`; id plus path -> `invalid_params`; id reuse after prune is blocked by the revision bump; double delete -> `invalid_params`.
- Junctions: delete of a junction removes only the link; the target keeps its content; traversing through a loop junction by path is refused; a junction swapped in for a folder after the scan is refused (`protected_path` / `stale_tree`).
- Move into itself, onto itself, onto an ancestor: refused. Delete while scanning: `not_enabled`. Cancel then delete and failed rescan keep a consistent tree.
- Control: malformed JSON, non-object, wrong key, missing key give structured errors, no panic.
- Performance at 1M nodes (release): preview of a 1M-child folder 11.2 ms, dry-run 11.8 ms, real delete with prune 28.5 ms; search budgets hold (10 s cap with `budget_exhausted`); regex compile with large classes stays bounded by the 1 MiB program limit.

## Regression-candidate tests (for the owner to adopt; not added to the repo)

Each fixture lives in a tempdir with `FakePlatform`.

1. `delete_refuses_aliased_names` (QA-116): create `dup` and `\\?\root\dup.` with equal size and mtime, scan, expect `file.delete` of either node to return an error and neither file to be touched.
2. `delete_refuses_lossy_names` (QA-116): create `x<U+D800>.tmp` and `x<U+FFFD>.tmp` with equal size/mtime, scan, expect the lone-surrogate node to have `name_lossy == true` and every destructive command on it to be refused.
3. `unc_guard_rejects_globalroot` (QA-117): `Dispatcher::handle_line` with `platform.free_space` and `scan.start` for `\\?\GLOBALROOT\Device\Mup\x\y` and `\\?\globalroot\device\mup\x\y`; expect `invalid_params` in under 100 ms.
4. `permanent_folder_delete_detects_deep_change` (QA-118): preview a folder, add a file two levels down, expect `stale_tree` on `file.delete_permanent` and the file still present.
5. `hardlinked_second_name_is_deletable` (QA-119): hardlink pair, scan, delete the second name by path and by id; expect success (or a documented "hardlink" refusal that does not say "size changed").
6. `cleanup_preview_has_budget` (QA-120): 40,000 nodes with 240-char names and 64 worst-case globs; expect return in under a configured budget with `budget_exhausted:true`.
7. `control_allows_backslashes_in_queries` (QA-122): `search.find` regex `\\d+` is accepted.
8. `move_refuses_reserved_names` (QA-123): destination `CON`, `COM1`, `aux.txt` returns `invalid_params`.

## Not covered

- MFT backend (needs elevation, not allowed); the portable backend only. QA-116 and QA-119 may differ on the fast path.
- Real recycle bin, `platform.reveal`, `platform.properties` (forbidden by the rules); `SystemPlatform` was only used for `free_space` on non-existent targets.
- `dirustat-cli run` with destructive commands was not executed (QA-124 is from code reading).
- NTFS ADS inside the tree, symlinks (only junctions tested; creating symlinks needs privileges), network volumes (only an unroutable TEST-NET address), volumes with case-sensitive directories, non-NTFS file systems.
- A true concurrent client test (two sockets issuing destructive commands in parallel) and MCP transport framing; only the dispatcher entry was driven, single-threaded.
- Fuzz targets and malformed MFT corpus (M4 does not touch the parser).
- wasm-core CI step (target not installed).
- The UI layer (covered by the separate `qa-ui-tester` run). Bug ids QA-116 onward were taken from the last id of the previous report; if the UI report allocated the same range, renumber one of them.

## Verdict

**NO-GO for the destructive commands as they stand (`file.delete_permanent`, `file.move`, `cleanup.run` with permanent action); GO with known issues for the read-only parts (search, platform.free_space on local paths, scan exclusions, preview/dry-run).**

Deciding bugs:
- QA-116 (S1, wrong target): must be fixed before any release that ships destructive commands.
- QA-118 (S2, unseen content deleted): at least permanent folder delete needs a subtree verification or a visible "subtree not verified" warning.
- QA-117 (S2, UNC guard bypass): replace the deny list with a positive path validator.

Safety go/no-go summary for destructive commands:
- Recycle-bin delete of a single file under a normal name: GO (confirm required, protected paths, revision checks, junction handling and journal all behaved as documented).
- Permanent delete, move and cleanups: NO-GO until QA-116 and QA-118 are fixed.
- Control/MCP exposure: GO with known issues only after QA-117 is fixed; today a keyed client can trigger network access and stall the session.
