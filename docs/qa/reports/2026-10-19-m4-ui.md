# QA report 2026-10-19 · M4 UI (search, drives, delete dialogs, cleanups, journal, preferences)

- **Commit:** 146ee68 (working tree had unrelated uncommitted edits in `crates/model`, `crates/scan`), release build with `CARGO_TARGET_DIR=target/agent-qa-ui`, Windows 11, not elevated. Tester: qa-ui-tester.
- **How:** channel-driven only (`ui.set_state`, `ui.state`, `ui.screenshot`, `engine.execute`, `session.state`) against `dirustat --demo --control <port>` (FakePlatform: no real recycle bin, Explorer or Properties) and tempfile fixtures in the scratchpad (small unicode/long-name tree, `xtask fixtures` 100k and 1m). Every PNG was looked at. Evidence: `docs/qa/evidence/ui-m4q-*.png` (synthetic data only; paths show the temp fixture location).
- **Covered:** search (modes, case, full path, size/extension filters, invalid regex and size messages, highlights, clear), start screen and drive picker, free space in the status bar, delete dialogs (recycle, permanent, partial-tree, scan root, scanning, long and unicode names) opened but never confirmed, programmatic `file.delete*` preflight errors (`protected_path`, `stale_tree`, `confirmation_required`), journal (25 entries, dark/light), Cleanups (built-ins, preview, engine-level save validation, user cleanups), Preferences exclusions, command palette, dark and light themes, 640x420 window, 200 % zoom, 100k and 1m trees (scan, search, `ui.state` latency), cancel mid-scan.
- **NOT covered (no mouse/keyboard driver was available):** real clicks, context menu on tree rows and treemap tiles, keyboard shortcuts (Delete, Shift+Delete, Ctrl+F, Ctrl+Shift+R, Alt+Enter, Ctrl+Shift+C), Enter/Escape/Tab behaviour in the dialogs (only code-read: `delete_dialog.rs` gives Cancel the initial focus and blocks Enter on the permanent confirm), disabled-menu tooltips, UNC root in the UI (UNC `scan.start` is refused over control by design), confirming a dialog (so the success/`stale_tree`/`protected_path`/`unsupported` toasts of the dialog were not seen; only the engine-level errors), Cleanups new/edit/remove form and inline validation (only `cleanup.save` validation through the engine), journal paging beyond one page (25 entries), real HiDPI scale (zoom 200 % used as a proxy), window larger than 1280x800, high-contrast theme (not implemented).
- Settings: `%APPDATA%\dirustat\settings.json` is written by the app even in `--demo`; it was backed up and restored. Test cleanups were removed. Fixtures were deleted.

## Bugs

### QA-125: Paths are cut at the end: the file name is never visible in the delete dialog list, journal and cleanup preview

- **Severity:** S3 · **Likelihood:** Always for paths longer than about 60 characters (any real user profile path) · **Scope:** all users
- **Area:** `crates/ui/src/delete_dialog.rs` (`path_list`, `.truncate()`), journal window, Cleanups preview · **Found by:** ui
- **Build:** 146ee68, release, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. `dirustat --demo --control 7993`; scan a folder with 30 files in a subfolder `many` (`engine.execute scan.start {"path": "<fixture>"}`).
2. `engine.execute select.node {"id": <many>}`, then `ui.set_state {"patch":{"delete_dialog":"permanent"}}`, `ui.screenshot`.
3. Also `ui.set_state {"patch":{"journal_open":true}}` after any recorded delete, and `{"cleanups_open":true,"cleanups_preview":"temporary-files"}`.

**Expected:** in a confirmation list the distinguishing part (the file name) is visible; shorten the middle or the start, or wrap, and show the full path in a tooltip.
**Actual:** every row shows only the common prefix `C:\Users\KrimsN\AppData\Local\Temp\claude\E--sandbox-tmp-windirstat-rust\...`. 30 rows in the dialog are indistinguishable; the user cannot see which files will be deleted. The journal Path column and the cleanup preview rows have the same problem. Tooltips were not checked (no pointer).
**Reproduces:** 4/4 (dialog on a folder, journal dark and light, cleanup preview).
**Impact:** the whole point of the confirmation list is to show what is deleted; this undermines the safety UX of M4.7 (`docs/safety.md`), hence S3 rather than S4.
**Evidence:** `ui-m4q-fx-del-partial.png`, `ui-m4q-journal-dark.png`, `ui-m4q-journal-light.png`, `ui-m4q-cleanup-temporary-files.png`

### QA-126: CJK file names render as tofu boxes everywhere

- **Severity:** S3 · **Likelihood:** Always for CJK names · **Scope:** all users with CJK (and some other) file names
- **Area:** theme fonts, tree, delete dialog, cleanups, preferences · **Found by:** ui
- **Build:** 146ee68, release, Windows 11
- **Status:** confirmed

**Steps to reproduce**
1. Create `日本語フォルダ/ファイル.txt` in a fixture folder and scan it.
2. Look at the tree row, then select it and open the dialog (`delete_dialog: recycle`); also save a cleanup named with CJK text and a CJK exclusion pattern.

**Expected:** readable names (system font fallback or an optional font); at least the delete dialog must show the real name.
**Actual:** boxes in the tree, treemap-selection, dialog title/path, cleanup name, exclusion list. Cyrillic is fine; the emoji folder shows a partial glyph. The user cannot verify what a dialog would delete.
**Reproduces:** 3/3.
**Impact:** unreadable names in a delete confirmation; wide user base (CJK Windows).
**Suspected cause:** no CJK fallback font loaded (a guess; fonts are not committed per AGENTS.md, so system font lookup would be needed).
**Evidence:** `ui-m4q-fx-del-cjk.png`, `ui-m4q-prefs-dark.png`, `ui-m4q-cleanups-user.png`

### QA-127: Status-bar notices never expire

- **Severity:** S4 · **Likelihood:** Often · **Scope:** all users
- **Area:** `UiState.notice`, status bar · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. Scan the 100k fixture; `scan.start` again and immediately `ui.set_state {"patch":{"delete_dialog":"permanent"}}` with a selection (notice "Wait for the scan to finish").
2. `engine.execute scan.cancel`, wait; or wait 12 s; or finish a new scan. Read `ui.state.notice` and take a screenshot.

**Expected:** a notice disappears after a few seconds or when the condition ends (scan finished or cancelled).
**Actual:** the red text "Wait for the scan to finish" stays next to "Scan cancelled" / "Scan complete", also after 12 s and after a later full scan. Same for "The scan root cannot be deleted" and the protected-path text (it stayed over a completed rescan). Only a successful delete clears it. The messages also live in the status bar, not as toasts as `docs/ui-design.md` describes.
**Reproduces:** 4/4.
**Impact:** contradictory state ("complete" and "wait") confuses users; no data risk.
**Evidence:** `ui-m4q-cancelled-2.png`, `ui-m4q-scanning-1.png`, `ui-m4q-fx-del-root.png`

### QA-128: Invalid size filter keeps the previous highlights in the treemap

- **Severity:** S4 · **Likelihood:** Sometimes · **Scope:** all users
- **Area:** search panel, `search.clear`/session hit set · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. `ui.set_state {"search":{"open":true,"query":"","min_size":"1 MB","max_size":"20 MB","extensions":"mp3"}}` (demo): 1 hit, the `.mp3` tile is outlined.
2. `ui.set_state {"search":{"min_size":"abc"}}`; `ui.screenshot`.
3. `engine.execute search.clear` returns `{"cleared":1}`.

**Expected:** error text shown and no highlight (as for an invalid regex, which clears them).
**Actual:** panel shows the error and `hits: []`, but the `.mp3` tile keeps its highlight outline; the session still holds 1 hit.
**Reproduces:** 3/3.
**Impact:** highlights contradict the empty result panel.
**Evidence:** `ui-m4q-stale-hl-2.png` (compare `ui-m4q-search-badregex.png`, which is correct)

### QA-129: Cleanup preview with `only_under` outside the scan root shows a delete-worded cryptic toast

- **Severity:** S4 · **Likelihood:** Sometimes (user cleanups saved before a different scan) · **Scope:** all users
- **Area:** Cleanups window, `cleanup.save`/`cleanup.preview` · **Found by:** ui
- **Status:** confirmed

**Steps to reproduce**
1. Scan a fixture. `engine.execute cleanup.save {"definition":{"id":"qa-x","name":"QA x","action":"recycle","selector":{"names":["*"],"only_under":"C:\\Windows"}}}` succeeds.
2. `engine.execute cleanup.preview {"id":"qa-x"}` gives `invalid_params: path does not resolve to a node of the scanned tree`.
3. `ui.set_state {"patch":{"cleanups_open":true,"cleanups_preview":"qa-x"}}`, screenshot.

**Expected:** a message that names the cleanup and its `only_under` folder ("outside the scanned folder"), worded for a preview.
**Actual:** toast "Cannot delete this item: path does not resolve to a node of the scanned tree"; the window still shows the previous preview.
**Reproduces:** 2/2.
**Evidence:** `ui-m4q-cleanups-onlyunder.png`

### QA-130: Cleanups window list is not refreshed for cleanups saved through the engine

### QA-133: Preferences: a long exclusion pattern pushes Remove out of the window

- **Area:** Preferences window · **Found by:** ui

### QA-138: Polish

- **Severity:** S5
- Sizes are floored, not rounded (47 998 000 B shows 45.7 MiB, the exact value 45.78 MiB).
- Empty session shows "1 nodes" in the status bar.
- `engine.commands` gives no menu or shortcut for `platform.reveal`, `platform.properties`, `search.clear` (UI has them) and reports `platform.*` and `search.clear` enabled without a tree or selection.
- Journal header says entries are appended to `journal.jsonl` in the settings folder, which `--demo` does not do.
- A single-item delete dialog prints the path twice (muted full path and a truncated monospace row).
- Disabled Enter on the permanent confirm gives no explanation (code-read only).
- `docs/ui-design.md` mentions a high-contrast theme that does not exist.
- Overlay "Previous scan - new scan in progress" is low-contrast over the dense treemap.

## Verdict

**GO with known issues** for the M4 UI in terms of data safety: no crash, hang or wrong target was found, engine-level preflight (protected root, stale file, revision checks, partial-tree flag in the dialog) behaves as documented, and 1m-node scan and search keep the UI responsive. Fix before release: QA-125 (file names invisible in the confirmation list) and QA-126 (CJK unreadable) because both weaken the deletion confirmation; the S4 items may ship as known. This verdict is conditional on a manual click-through of the uncovered items (shortcuts, context menu, dialog confirm/Escape/Enter, cleanup editor), which this run could not perform. One unexplained event: a test instance disappeared once after a 1m-node search session (no panic text in its log, not reproduced in 2 further runs); treat as unconfirmed.
