## The reported resize bug: root cause

The "window resize breaks directory and file blocks" report is **two cooperating defects in `treemap::layout_tree`** (`crates/treemap/src/lib.rs`):

1. **QA-2 / QA-101 (cap starvation).** The work list is a LIFO `Vec` and children are pushed largest first, so the smallest directories are expanded first. When `max_tiles` (50 000) is reached, the biggest directories stay as flat empty blocks. A bigger window yields more tiles of at least 2 px, so the cap is hit earlier and more holes appear. Shrinking the window recovers the detail; a rescan does not. Reproduced by the UI tester 4/4 on 100k and 1M fixtures (maximized window), and by the lead by code reading (`lib.rs:173-199`).
2. **QA-1 (dropped tiny children).** Children below `min_size` are skipped, the parent is marked `leaf = false`, and `map_panel` paints non-leaf tiles as a frame only (`map_panel.rs:174`). The dropped share shows the background, and its size depends on the viewport. Confirmed by the lead by code reading.

Layout cache key, DPI and stale rects were ruled out by both testers. QA-102 (2.4 s UI freeze per resize step on 1M nodes) makes the resize experience worse.
