# QA report 2026-10-23 · M5 UI

- **Commit:** 8f8783a (tree clean), release build (`CARGO_TARGET_DIR=target/agent-qa-ui`), Windows 11 Pro 10.0.26200, not elevated, 2560x1440 display. Tester: `qa-ui-tester`.
- **Data:** synthetic only: `cargo xtask fixtures --size small` and `--size 100k`, plus temp trees built by the tester (real byte-identical duplicate files, 6 x 120 MiB identical files, unicode and 180-character names, 300 duplicate pairs, an empty folder, a vanished folder). Everything lives under `E:\sandbox\tmp\qa-ui-fx\` (outside the repo). No destructive command was run (the delete, move and cleanup calls made under a shown snapshot were all refused). No native dialog was opened and no real folder or drive was scanned or screenshotted.
- **How it was driven:** control channel (`engine.execute`, `session.*`, `ui.state`, `ui.set_state`, `ui.screenshot`) from a small Python client, plus Win32 `SetWindowPos` calls to resize and maximise my own app window. Evidence: `docs/qa/evidence/ui-m5-*.png`.

## Covered (channel-driven)

- Preferences > Treemap: checkboxes, six sliders, reset (via `treemap.cushion|grid|free_space|look`), extreme and invalid values, dark and light themes, small and tiny windows, zoom 200 and 300 percent.
- View > Grid lines, Free space band: needs a local root (E:), band width, label, narrow windows, band with empty and vanished roots, selection with the band on.
- Cushion shading: background-pixel scan, theme switch, maximised window, 100k tree, 300 rapid look changes and 90 rapid toggles.
- Export (`export.csv|json|png`), validation and output files. Snapshot save, load, list, compare, close. Snapshot shown: status label, refusals, delete dialog refusal, rescan afterwards, `selection_lost` toast.
- Duplicate finder: criteria validation (engine side), progress, cancel, paging (302 groups), selection sync with tree and treemap, empty/idle state, no delete button, closing the window during a run, quit during a run (clean exit, key file removed).
- Scan scenarios: cancel, missing folder, "not a folder", empty folder. UI latency during scan, snapshot save/load, PNG and JSON export on 100k nodes.

## NOT covered

- No mouse input reached the app: a posted click did nothing and a real synthetic click was refused by my own safety check (another window had the foreground). So **not tested:** menu clicks (File > Export, File > Snapshot, View items, Tools items, Delete menu entry), keyboard shortcuts, dragging sliders, hover tooltips (band and tile tooltips, hit-testing by pointer), double-click zoom, clicking Find / Cancel / Compare / Previous / Next buttons in the windows, the native save/open dialogs, the result list of the Compare window, scroll behaviour of the Preferences window in a small window (no scrollbar is visible without hover), and duplicate criteria validation messages in the window (fields are not reachable by `ui.set_state`; only engine-side validation was exercised). Menu paths and shortcuts were checked only against `commands.rs` and `engine.commands`.
- `ui.*` commands (`ui.duplicates`, `ui.export_*`, `ui.compare`, ...) are not executable through the control channel by design.
- No HiDPI OS scale other than egui zoom; no screen-reader check; no real NTFS fast path or access-denied or cyclic-link scenario (covered by the code tester).
- Environment note: the app window was minimized by something outside the app several times during idle periods (no minimize code exists in `apps/` or `crates/ui`; `ui.screenshot` then times out with its documented message). It happened with no input from me and is not counted as a bug; I restored the window before every capture.

## Bugs

### QA-250: Selection outline of a folder is missing on the treemap at smaller window sizes

- **Severity:** S3 · **Likelihood:** Often (every window narrower than roughly 800 px or shorter than roughly 400 px) · **Scope:** all users, any theme
- **Area:** `ui::map_panel` selection outline, `select.node` of a directory · **Found by:** ui
- **Build:** 8f8783a, release, Windows 11, not elevated
- **Status:** confirmed

**Steps to reproduce**
1. `dirustat --control 47900`, `engine.execute scan.start {"path":"E:\\sandbox\\tmp\\qa-ui-fx\\small"}` (fixture from `cargo xtask fixtures --size small`).
2. Resize the window to 760x560 (drag it, or `SetWindowPos`).
3. `engine.execute select.node {"id":12}` (folder `dir_22_1`, 36 % of the map), wait 2 s, `ui.screenshot`.
4. Repeat at 900x650 and compare.

**Expected:** a 2 px accent outline around the folder tile in the treemap, as at 1200x800 (selection is synchronised between tree, map and list).
**Actual:** the tree row is highlighted but the map has no outline (at most a stray 2-3 px blue tick). Measured by counting accent-coloured pixels (about 2000-3000 with an outline, 52-108 without):

| Window | Outline |
|---|---|
| 900x650, 800x600, 1000x450, 1000x400, 900x400 | yes |
| 790x570, 780x560, 760x560, 700x520, 640x480, 420x380, 330x300, 1000x300 | no |

Folders 11, 12 and the root (ids 11, 12, 1) all fail at 1000x300. A file tile selected at 760x560 does show its outline (`ui-m5-sel-outline...` shows both). The result is deterministic for a given size. It also fails with the free-space band on and off.
**Reproduces:** 5/5 runs at 760x560 and 1000x300 (and the whole table above, run twice)
**Impact:** selecting a folder in the tree gives no visual feedback on the map in half-screen or small windows, which breaks the documented tree/map selection sync for the main object type. Not data-affecting, a workaround exists (enlarge the window), so S3.
**Suspected cause / pointer:** guess: the outline is drawn from `layout.tiles()` of the view that `MapState::scaled` rescales from a quantised-bounds cache (`crates/engine/src/map.rs:67`), and the folder tile rect degenerates for some bounds; see `crates/ui/src/map_panel.rs:309`.
**Evidence:** `docs/qa/evidence/ui-m5-sel-outline-by-window-size.png` (900, 640, 420 wide), `ui-m5-sel-outline-missing-760x560.png`, `ui-m5-sel-outline-missing-1000x300.png`

### QA-251: Background pixels show at the bottom edge of the treemap and of the exported PNG

- **Severity:** S4 · **Likelihood:** Sometimes (3 of 8 in-app runs, 2/2 PNG exports) · **Scope:** all users
- **Area:** `ui::cushion_view` renderer, `export.png`; `docs/ui-design.md` says no background pixel shows inside the tree · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. Build a temp tree: 3 identical 3 MB files, 2 other 3 MB files, 40 small files, 600 small text files (the tester's `dup` fixture; any similar mix works).
2. `scan.start` it in a 1200x800 window (grid off, free band off), wait 2.5 s, `ui.screenshot`.
3. Count pixels equal to the background colour (17,19,22) inside the map rectangle.
4. `engine.execute export.png {"path":"E:\\sandbox\\tmp\\qa-ui-fx\\out\\a.png","width":600,"height":400,"overwrite":true}` and count the same.

**Expected:** 0 background pixels (the renderer closes one-pixel gaps).
**Actual:** in-app: 28 pixels in the last map row (y=729, x 908..935) on repeated scans of the same folder (7 pixels in an earlier run with grid on; 0 in three other runs). PNG: 12 pixels in the last row (y=399, x 588..599), identical in the dark and the light export.
**Reproduces:** PNG 2/2; in-app 3 of 8 scans of the same unchanged tree
**Impact:** a visible 1 px dark line at the bottom edge, rare and cosmetic, but it contradicts a documented M5.6 guarantee.
**Suspected cause / pointer:** guess: last row or column of the rounded tile grid in `cushion_view::render` is not covered when the float edge rounds down.
**Evidence:** `docs/qa/evidence/ui-m5-export-png-dark-light.png` (bottom-right corner, the pixel strip is visible only when zoomed)

### QA-252: Ambient 0 and diffuse 0 give an all-black treemap, reachable from the sliders

- **Severity:** S4 · **Likelihood:** Sometimes (needs two sliders at zero) · **Scope:** all users
- **Area:** Preferences > Treemap, `treemap.look` · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan any fixture.
2. `engine.execute treemap.look {"reset":true,"ambient":0,"diffuse":0}` (both are inside the documented 0..=1 range; the sliders reach the same values).
3. `ui.screenshot`.

**Expected:** the map stays usable (or the UI warns), the colours of the extensions stay distinguishable.
**Actual:** the whole map is pure black, no tile can be told apart, and there is no hint in Preferences. "Reset cushion look" is the only way back. `ambient 1 / diffuse 1` is washed out but readable; height 0, scale 0, light at the horizon and straight-on light all render sensibly.
**Reproduces:** 2/2
**Impact:** self-inflicted and one click to undo, hence S4. A floor on `ambient + diffuse` would avoid it.
**Evidence:** `docs/qa/evidence/ui-m5-look-extremes.png` (third tile, "look-dark0")

### QA-253: Duplicate window shows the previous result list while a new search runs

- **Severity:** S4 · **Likelihood:** Often (every second search) · **Scope:** all users
- **Area:** Tools > Duplicate files window (`duplicates_ui.rs`) · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan a folder with duplicates, `ui.set_state {"patch":{"duplicates_open":true}}`.
2. `duplicates.find {"min_size":1}` and wait until `duplicates.status` is `done` (the window lists the groups).
3. `duplicates.clear` is not called; start a second search: `duplicates.find {"verify":true}` and take a screenshot while `state` is `running`.

**Expected:** the old list is cleared or clearly marked as old while the new search runs (the engine already answers `not_enabled` for `duplicates.results` then).
**Actual:** the status line reads "Comparing files byte by byte: 2 of 6 files..." while the list below still shows the finished groups of the earlier search ("6 copies of 120.0 MiB - 600.0 MiB wasted"). A related oddity: the window criteria field still says "Minimum size 1 MB" although the result shown was produced by a control call with `min_size: 1`.
**Reproduces:** 2/2
**Impact:** the user may click an entry of an obsolete list. Read-only, so S4.
**Evidence:** `docs/qa/evidence/ui-m5-dup-stale-results-while-running.png`; for the normal finished state see `ui-m5-dup-selected.png` (selection syncs with tree and map, no delete button, Delete hint only).

### QA-254: Duplicate window clips long paths at the edge instead of eliding the middle

- **Severity:** S4 · **Likelihood:** Sometimes (long paths) · **Scope:** all users
- **Area:** Tools > Duplicate files window; `docs/ui-design.md` M4.9 "paths are elided in the middle, the file name always stays visible" · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan a folder containing a file named `name_` + 180 `x` + `.bin` that has a duplicate (same content).
2. Open the Duplicate window (`duplicates_open: true`), run `duplicates.find {"min_size":1}`, screenshot.

**Expected:** `E:\...\name_xxxx...xxx.bin` with the tail visible and the full path as hover text.
**Actual:** the row runs to the window edge and is cut mid-name; the end of the name is invisible. (Unicode and CJK names render correctly.)
**Reproduces:** 2/2
**Impact:** you cannot tell long names apart; cosmetic, S4.
**Evidence:** `docs/qa/evidence/ui-m5-dup-selected.png` shows the normal rows; the clipped row is in the 22-copies group of the same window (screenshot `dup-pages`, not kept, reproduce with the steps above).

### QA-255: `engine.commands` reports `enabled: true` for commands that a shown snapshot refuses

- **Severity:** S4 · **Likelihood:** Always while a snapshot is shown · **Scope:** control and MCP clients
- **Area:** `engine.commands` `enabled` field vs `admit` · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. Scan a temp folder, `snapshot.save` it, `snapshot.load {path}` (shown).
2. `engine.commands`: read `enabled` for `file.delete`, `file.delete_permanent`, `file.move`, `cleanup.run`, `duplicates.find`.
3. `engine.execute file.move {...confirm:true}` etc.

**Expected:** `enabled: false` (docs/safety.md: the UI "disables Delete with a reason" and `admit` refuses).
**Actual:** all five report `enabled: true`; each execution answers `not_enabled` ("the tree is a saved snapshot, not the live disk; scan the folder again or close the snapshot"). The refusal itself is correct and the reason text is good; the UI menu and `ui.set_state delete_dialog` also refuse with a notice ("This is a saved snapshot, not the live disk: scan the folder again to delete files"). Nothing was deleted.
**Reproduces:** 3/3
**Impact:** an agent or MCP client that trusts `enabled` is misled; no safety impact. S4.
**Evidence:** JSON from steps 2 and 3 (see report text)

**Steps to reproduce**

### QA-257: Free-space band: empty scan leaves half the panel blank; a vanished root gives no feedback

- **Severity:** S4 · **Likelihood:** Sometimes · **Scope:** all users with the band on
- **Area:** View > Free space, `map_panel` · **Found by:** ui
- **Build:** 8f8783a, release
- **Status:** confirmed

**Steps to reproduce**
1. `treemap.free_space {"enabled":true}`; scan an empty local folder; screenshot.
2. Scan a temp folder, `snapshot.save`, delete the folder, `snapshot.load`; screenshot.

**Expected:** an empty-state message in the map and a band that is not given half the width when nothing was scanned; some hint when the band cannot be shown.
**Actual:** 1: the left half of the map is a blank rectangle (the tree says "The scanned folder is empty", the map says nothing) and the band is 50 % wide (free/(0+free) clamped). 2: the setting is on, but neither band nor message appears and the status bar shows no free-space text; `ui.state.free_space` is `null`. Note also that for any folder much smaller than the free space the band is always the clamped 50 %, so its width carries no information (by design per `ui-design.md`, but worth a usability thought).
**Reproduces:** 2/2
**Impact:** unclear UI in edge cases, S4.
**Evidence:** `docs/qa/evidence/ui-m5-empty-scan-band.png`, `ui-m5-snapshot-missing-root-band.png`

### QA-258: Polish list (S5)

- **Severity:** S5 · **Likelihood:** see each item · **Scope:** all users
- **Area:** various · **Found by:** ui · **Build:** 8f8783a · **Status:** confirmed

1. Cancelling a duplicate search (via `duplicates.cancel`) returns the window to the idle text "Press Find duplicates..." with no "Cancelled" message. "1 groups" is not pluralised.
2. The selection-lost toast says "gone after the rescan" even when a different folder was scanned (scan `small`, select a file, scan `dup`). Loading a snapshot clears the selection silently (no toast, `selection_lost` null), whereas a rescan carries the selection by path.
3. Preferences, Duplicate files and Compare windows open at the top-left with their title bar overlapping the lower half of the menu bar.
4. The Light elevation slider cannot show values under 5: `treemap.look {"light":[100,100,0]}` or `[1,0,0.001]` show "5.00" while the real value is 0 or about 0. Opening Preferences does not write back, but dragging probably does.
5. Toolbar at about 330-420 px width clips "Size: logical" and hides "Drives" without an overflow menu.
6. Tree name column clips text without an ellipsis; the root row shows "E:\sandbox\tm" (the full scan path, cut) instead of a readable name.
7. After a snapshot load the map shows flat unshaded tiles for about a second before the cushion image arrives.
8. `ui.set_state {"delete_dialog":"recycle"}` answers `ok: true` although the dialog was refused (notice only).
9. `ui.state` carries no treemap settings (cushion, grid, free band, look); only `settings.get` does. `ui.state` is not accepted whole by `ui.set_state` (read-only keys such as `cleanups` are rejected as unknown fields).
10. Export PNG `theme: light` differs from dark by 113 pixels only: tile colours are the same in both themes (the same is true in the app), only background and panels change.

**Evidence:** `docs/qa/evidence/ui-m5-band-narrow.png` (item 5, 6)

## Checked and OK (for the record)

- Preferences > Treemap (dark and light, 100 to 300 percent zoom): checkboxes mirror the View menu settings, reset restores defaults, invalid look values (out of range, wrong array length, zero light vector, unknown field) are `invalid_params` with a clear message and nothing changes; 300 random look calls and 90 toggles in a row left the app responsive (`ui.state` latency 26-41 ms during scan, save, load, PNG and JSON export of 100k nodes).
- Free-space band on a local root: 50 % clamp, label at 80 px or more, hidden label below, stripes in both themes; selection outline and tile layout stay inside the left part.
- Snapshot: round trip of 100k nodes gives an identical tree (root and children compared), "SNAPSHOT (read-only)" label in the status bar (amber), delete/move/cleanup/duplicates refused with a reason, `compare base live` refused while shown, bad files (truncated, garbage, empty, flipped byte) are `invalid_params` with no dialog and no state change, rescan ends the view.
- Duplicates: results paged correctly (302 groups, no overlap, offset beyond the end is empty, limit 201 and stale revision refused), cancel mid-run works, closing the window does not cancel the job (finishes `done`), app quit during a running search exits cleanly in 0.03 s and removes the key file.
- Scan: cancel gives "Scan cancelled" and keeps the old tree, missing folder and not-a-folder show a red status message and keep the old tree.
- No programmatic call opened a dialog.

## Verdict: GO with known issues

No S1 or S2. The deciding item is QA-250 (S3): selecting a folder shows no outline on the map in windows smaller than about 800x450; it should be fixed or accepted by the owner before release. QA-251 to QA-257 are S4 and can ship. The large parts of the M5 UI that need pointer input (menus, dialogs, buttons in the Compare and Duplicate windows, tooltips, hit-testing in the left part of the map) were not exercised and need a manual pass before the verdict is final.
