## 2026-10-23 · M4.11 · G-062 lock-free deletes and cleanups · Claude
- Landed (engine): `cleanup.run` is now a chain of detached jobs (`cmd/cleanup.rs`: `begin_run`, `advance`, `finish_step`, `finish`). Each target is checked under the session lock right before its action, the action (recycle, permanent removal, reveal) runs without the lock, the outcome is journaled under it; the removal slot (`removal_in_progress`) is held for the whole non-dry run; the tree is pruned once at the end, and a revision change between two actions stops the run with `rescan_recommended`. `Session::execute` drives the same steps in one borrow (no second implementation). `finish_job` now returns `Prepared` (a cleanup hands back its next step); new `dirustat_engine::execute_unlocked(lock, id, params)` is the loop, used by the control dispatcher. `file::perform` removed; `act_with` takes the platform instead of the session. Busy refusal text: "a deletion is still running".
- Landed (UI): the delete dialog's confirm sends its command (`file.delete`, `file.delete_permanent`, `cleanup.run`) to a worker thread through `execute_unlocked`; the dialog shows a busy row with a spinner, cannot be cancelled (Escape, Cancel and `ui.set_state` close are ignored) and gets the answer in `finish_confirm`. `ui.quit` and the window close button are refused while a deletion runs. `platform.free_space` for the status bar is asked on a worker thread as well. `block_reason` refuses new deletions while `removal_in_progress`.
- Review (never-crash-reviewer subagent): nothing serious; four findings fixed in the same arc: `file.delete` (recycle) now gets the same detached removal job as `file.delete_permanent` (the shell recycle of a big folder froze the window); quitting and the close button are held off during any deletion, also one a control client started (`removal_in_progress`), since ending the process would cut it off half way; an ignored dialog close sets a notice; a cleanup step is journaled before anything else.
